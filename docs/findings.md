# 第二位 Top 真人猎头克隆：发现与证据

## 新分支范围（2026-08-07）
- 用户确认：Looper 访谈中可克隆的电话内回应策略和直接话术数量有限，不应继续把全部价值压缩成完整电话决策树。
- 新的四个提炼方向：端到端 AI 猎头长链路框架、匹配逻辑、二次通话逻辑、知识库。
- 匹配逻辑是当前最重要的后续讨论主题；本小组暂未负责匹配，但预计后续会接手，需要先从 Looper 提取可证实维度。

- 输出必须区分四种证据层级：Looper 明确陈述、跨段可拼结构、AI 为讨论做的抽象、需要用户/真人确认的问题。

## 新分支首轮证据（学习1全部 Looper 发言 + 学习2前半）

### 端到端长链路
- 【学习1 01:24:08】Looper把业务漏斗描述为：寻访量足够大 → 获得信息 → 加微信 → 拿简历 → 推荐给企业 → 跑出交付漏斗 → 产出业绩。说明“电话”只是链路前端，不是独立系统终点。
- 【学习2 24:02】Looper进一步把猎头业务抽成五个行为：寻访、转换、推荐、面试、Offer；寻访/推荐的直接目标是让候选人进入面试。
- 【学习2 25:51】Looper把刷库概括为“数据清洗和数据标注”。这提示系统前端不只是通话，还在持续生成/修正可供后续模块消费的数据。
- 【学习1 01:06:11-01:10:24】Looper明确区分两种业务风格：结构化、高频、短通话的规模型路径；低频、长聊、深挖、mapping、转介绍的深度路径。其判断是 AI 更适合前一种“量足够多、结构清晰”的方式，但大模型可承担其“拿线索—推理”的部分。

### 匹配逻辑
- 【学习2 01:55-03:23】匹配不是只看技能词；先读客户合同收费级别、年龄/年限限制，再用候选人年龄、毕业时间、title、工作年限反推职级，判断是否值得联系。
- 【学习2 09:08-10:24】业务匹配的重要性随职级变化：P6更看 Coding、高并发、分布式、Java主流栈；P7及以上必须继续看商业化、广告、增长等业务方向。
- 【学习2 11:54-18:06】候选人职级不能只看当前 title；需结合年龄、毕业时间、公司职级体系、项目亮点、创业经历、客户给 Offer 的习惯。输出是概率判断，不是确定事实。
- 【学习2 22:31-24:02】“能进入面试”与“最终拿 Offer”分开：电话前只需判断其背景是否达到客户标准、是否有进入面试的概率；最终能力由多轮面试验证。
- 【学习2 29:23-30:12】同为 C++ 不等于业务匹配；流媒体 C++ 与大模型 Agent C++ 的任务、场景和技术问题不同。匹配需要从技能标签下钻到业务场景、问题类型和项目目标。
- 【学习2 38:32-40:27】还需考虑竞业与薪资可落地性；“技术匹配”不等于“可成交/可落地”。

### 二次通话
- 【学习1 01:13:27-01:14:46】首次拒绝后不能第二天重复联系；应记录号码/候选人信息，对重要且合适者换到周五晚上、周末下午等更放松的时间。
- 二次联系资格目前至少包含：候选人很合适/有进入面试概率、首次可能只是时间状态不佳、没有强烈反感；具体完整门槛仍需从学习2后半继续取证。

### 知识库线索
- 客户侧：合同收费起点、目标职级、年龄/年限规则、用人偏好、Offer/定级习惯、竞业关系。
- 候选人侧：年龄、毕业时间、学历、title、公司/团队、工作年限、项目亮点、创业经历、业务方向、技术场景、薪资和竞业。
- 市场/组织侧：公司新闻、业务调整、管理变化、团队人员流动；Looper会把这些用于话题和假设，但其真实性与时效需要单独记录。
- 过程侧：历史联系时间、候选人是否记得号码/音色/话术、拒绝原因、当前状态、是否已经聊过/面过某岗位。

## 新分支补充证据（学习2后半）

### 匹配的分层对象必须拆开
- 【学习2 49:22-51:44】Looper明确区分“优质候选人”和“匹配当前岗位”：小红书稳定履历可以说明人选优质，但业务方向未知时无法给当前岗位匹配分，必须通过电话核实。
- 【学习2 55:24-57:14】候选人质量四维：学历、公司背景、稳定性、职级；公司背景可覆盖稳定性解释，核心团队的一年一跳不一定被视为频繁跳槽。业务方向不是人选质量维度，而是“有没有相应客户/资源”的匹配维度。
- 【学习2 01:17:38-01:18:56】历史迁移路径本身可以提供行为和能力假设：例如从花旗长期任职转到蚂蚁，Looper推测其主动求变、开放，且技术能力可能经过更高门槛验证；但这仍是经验概率，不是确定事实。
- 【学习2 01:18:56】同一候选人可对“金融/支付”岗位合适、对“商业化广告”岗位不确定，说明匹配输出必须是“候选人×具体岗位/客户”的关系分，而非候选人单一总分。

### 二次通话的核心变化
- 【学习2 01:05:52-01:07:02】首次触达采用开放问题或选项；如果候选人态度不理想并快速结束，二次触达改为最短路径：直接呈现手里有哪些机会并问“你看不看”。看则继续，不看则停止。
- 【学习2 01:07:54】候选人的状态会随心情、工作事件和客观处境变化；昨天不看不代表今天不看。因此二次通话不是重复第一次判断，而是利用新时间点重新验证需求—资源是否对上。
- 【学习2 53:26-54:35】候选人主动说“一个月后再联系”应成为明确的后续时间状态；对于优质且有看机会信号的人，可以换到更晚或周末再触达。
- 【学习2 59:29】“之前约过电话”可能触发承诺一致性，提示二次通话应携带并使用上一通的约定，而不是当作陌生首呼。

### 客户画像/公司标签是更稳定的知识层
- 【学习2 01:24:27-01:26:22】Looper认为客户属性、喜好和特点相对固定，比候选人当下心情更容易标准化；从客户角度寻访，应先理解客户再提高效率。公司标签应分大类，不能细到失去可维护性。
- 【学习2 01:27:22】公司级比较要控制粒度：大型多业务公司不能直接与单业务公司整体比较，只能用相应业务团队对比。知识库实体至少需要“公司—业务线/团队”层级。
- 【学习2 01:29:01-01:29:29】Looper明确给出三类知识来源：公开新闻/公众号、人选反馈、客户信息；客户侧还要深究招聘动向、为什么招人、满足什么诉求、内部发生了什么。
- 【学习2 01:30:17-01:42:01】公司标签示例维度：薪资水平与相对市场位置、年龄包容度、裁员/稳定性、业务增长与组织折腾程度、工时、心理压力、适合的职业阶段、家庭和现金需求。公司标签的用途是与候选人诉求对齐并支持转换，不是统一褒贬。
- 【学习2 01:44:42-01:49:31】Looper把资深猎头优势描述为大量难以言传的经验/肌肉记忆，并认同“把过往所有知识体系结构化”；这直接支持建设可复用知识库，而不只是话术库。

### 端到端框架的进一步抽象依据
- 【学习2 07:18】当时 AI 寻访阶段的目标以加微信为主；这只是当前阶段目标，而非猎头系统最终目标。
- 【学习2 32:16-36:47】候选人显露需求后，系统要从“意愿识别”切换到“资源证明/我有货”，再加微信、发资料，进入后续互动。
- 【学习2 34:31】加微信有时是为未来岗位建立储备资源；候选人不一定立即匹配现成岗位，系统需要人才池和未来机会触发机制。
- 综合两次访谈可拼出但需标记为“结构抽象”的长链：客户/岗位建模 → 人才库清洗与优先级 → 首次触达与信息补全 → 意愿/需求识别 → 资源匹配与转换 → 加微信/简历 → 推荐 → 面试 → Offer；期间候选人和客户知识持续回写。

### 原始上下文核对后的归属边界
- 【学习2 24:02】“寻访、转换、推荐、面试、Offer”五行为是 Looper 明确亲口总结，可作为端到端业务骨架的一级结构。
- 【学习2 25:16】“批量打完记录接通/挂断，再筛优质人晚上重打”的详细流程来自发言人8，不是 Looper；Looper只在 25:51 将该过程概括为数据清洗和数据标注。正式提炼不得把发言人8的细节归到 Looper。
- 【学习1 01:12:18】Looper关于“产品最后愿景”的句子在转录中语义未完结，必须与上下文合用，不能单独当作完整系统定义。
- 【学习2 07:18】“当前 AI 寻访目的以加微信为主”是在评价当时产品阶段；必须与五行为终局骨架分开，避免把阶段 KPI 当成系统终局。
- 【学习2 55:24-57:14】四维评判是在回答“怎么判断候选人”的明确问题，证据强；其中业务方向被 Looper 明确排除出候选人质量评判，转入资源/岗位关系匹配。
- 【学习2 01:28:51-01:29:29】三类知识来源是在被问“如何持续更新大量公司/业务部信息”时直接作答，适合成为知识库来源模型的核心证据。

### 二次通话内部存在的待讨论矛盾
- 【学习2 01:05:52】Looper说二次触达直接抛资源，“看”则继续，“不看”则这个人可能没必要继续；这是单次二次通话内的停止判断。
- 【学习2 01:07:54】紧接着被问“二次仍未成功以后是否还继续尝试”，Looper回答“我觉得是会的”，理由是候选人状态每天变化。这说明“本次不继续聊”不等于“永久从未来触达池删除”。
- 因而二次通话至少要区分两个层级：通话内终止条件 vs 跨周期再激活资格。Looper没有给出最大次数、冷却周期或永久停联阈值，这些是明确的信息缺口。
- 【学习2 53:26、59:29】候选人主动给出的回拨时间和上一通承诺属于强状态，应在二次通话中继承；但 59:29 的句子被转录截断，不能推导完整话术。

### 公司知识库的候选维度（仅来源于 Looper 段落）
- 客户/公司基本属性：体量、业务范围、业务线/团队、招聘目标、职级与收费规则、年龄和年限接受范围。
- 回报：薪资水平、现金占比及其相对市场位置（“第一梯队但非顶尖”等相对标签）。
- 风险与稳定：裁员历史、业务结构是否稳定、是否频繁调整、项目/团队存续。
- 工作体验：工时、实际工作节奏、身体疲劳、心理压力、技术氛围和组织增长速度。
- 发展：平台背书、业务场景丰富度、技术成长、职级成长、适合的职业阶段。
- 适配人群：现金刚需、求稳/求成长、年龄段、家庭与定居状态、身体状态、野心/变化偏好。
- 这些标签的使用方式不是“公司统一打分”，而是与候选人诉求做关系匹配；同一标签对不同候选人可以是正向或负向。

### 匹配逻辑的初步层级（证据支持）
1. **商业可做门槛**：客户是否收费、目标职级、年龄/年限限制、地点、竞业、薪资能否落地。未过这一层，即使技术看起来相关也可能没有联系/推荐价值。
2. **候选人质量**：学历、公司/核心团队背景、稳定性、职级领先度。该层回答“是否值得持续接触和储备”，不直接回答当前岗位是否匹配。
3. **职级推断**：显式 title + 年龄/毕业时间/工作年限 + 公司职级映射 + 项目/创业例外 + 客户定级习惯；输出应是概率与证据，不是确定标签。
4. **岗位关系匹配**：技术栈、业务方向、业务场景、实际解决的问题、项目目标；同一候选人对不同岗位分别判断。
5. **候选人诉求—公司标签匹配**：薪资、工时、心理压力、稳定、成长、家庭/定居、身体状态和职业阶段与公司/团队属性对齐。
6. **可转换/可落地**：候选人当前意愿、活跃信号及宏观事件、竞业、薪资、地点、时间窗口、资源是否存在。
7. **后续验证**：电话补齐未知业务和诉求，面试验证真实技术能力；匹配分应随新证据更新。

### 匹配模型不能使用一个混合总分的理由
- Looper的表达同时包含“候选人质量”“客户标准”“当前岗位关系”“可落地性”四种不同对象；把它们混成一个分会掩盖问题来源。
- 示例：优质小红书候选人可以候选人质量高、当前 Agent 岗位匹配未知；拼多多候选人可以技术相关但竞业/薪资落地低；P6候选人可以技能合适但不满足客户收费职级。
- 因此后续讨论更适合先建立多阶段 Gate + 分维度关系评分，再讨论是否需要汇总分；这是基于 Looper 材料做的讨论抽象，不是 Looper 明示的公式。

## 已确认要求
- 当前先完整读取结构化策略文档；只有信息不足时才读取完整交流记录。
- 只依据资料内部信息提取节点与跳转，不用外部经验补全。
- 当前交付物仅包括：待确认节点表、待确认边表、信息缺口和冲突。
- 用户确认前不得生成最终评估 Prompt。
- 决策图拍板后，才映射真人原话并提炼功能顺序、句法结构、措辞语感。
- 最终必须分别输出策略执行分、话术质量分和综合分；综合分为策略 60% + 话术 40%。
- 话术质量内部权重为功能与顺序 50%、句法结构 30%、具体措辞 20%。
- 节点评分使用 0/25/50/75/100 锚点；无法可靠判断时用 N/A，且 N/A 不作为 0 分。
- 策略选错/跳转错误/漏节点只扣策略分；节点正确但表达不佳只扣话术分。

## 证据优先级
1. 真人明确确认的决策图。
2. 结构化策略文档。
3. 完整交流记录。
4. AI 推断（只能单独标记并待用户确认）。

- 评分本体包含约 24 条命名原子规则和一个可选观察项，规则字段实际已具备结构化 schema 雏形：`rule_id`、`node_id`、`dimension`、`weight`、适用条件、PASS/PARTIAL/FAIL/NA、证据、期望/实际下一节点、原因。
- 四个评价维度是 `PATH_BRANCH`、`REQUIRED_ACTION`、`BOUNDARY_COMPLIANCE`、`CLOSURE_FOLLOWUP`；权重 1/2/3 是工程口径，不宣称来自 Kiki 原话。90/75/60 为 verdict 阈值，也属于评价层配置。
- Prompt 将“策略知识”“评价政策”“运行输入契约”“JSON 输出 schema”“去重/依赖图”全部放在同一个文本中。产品化时最好拆为不同版本化对象，否则每次节点或话术局部更新都要重写整份 Prompt，难做稳定 diff 与回归。
- 真实性 guard 单独处理：专家访谈、资源/反向 BD、画像事实、CRM 动作、频控决定均要求外部输入；只有 AI 自述时不能确认 guard。说明完整评价产品的输入端不应只有通话转录，而应允许画像、岗位、历史触达、CRM/平台日志和资源事实清单。
- 严格 JSON 输出已经很适合成为下游 API 契约；其中 `observed_path`、`rule_results`、`critical_violations`、`unscored_unknowns`、`available_inputs` 等字段可直接成为未来流水线的中间数据，而不只是最终报告。
- 当前 Prompt 没有“知识版本/Prompt 编译来源/策略基线哈希/适用猎头或策略层 ID”等可审计元数据；`schema_version` 只标评价输出版本，无法回答一次评分用的是哪版知识。

## 2026-08-12｜Looper 话术知识的结构化程度
- 每个可评话术节点已经拆成：节点 ID/名称、真人原话、录音位置、功能顺序、句法骨架、措辞与语感、合法变体/槽位、边界和反例。这实际上就是一个可机器化的 `utterance_template` 数据模型。
- 同一原话可能覆盖多个节点，Prompt 已用“优先整体匹配/路径标签优先/无法区分时联合标签/同一实例只计一次”处理重合。这说明话术库必须允许 many-to-many：一条证据原话 ↔ 多个策略节点，一个话术实例 ↔ 一个主评分模板（可带候选模板集合）。
- 值得警惕：部分 Looper 原始策略包含编造人名、内部变化、公司/岗位资源等高风险内容；话术 Prompt 刻意不评真实性，只评表达形态。这再次证明未来产品需要独立的事实/合规 guard，不能把“像真人”当成“正确可用”。

## 2026-08-12｜Kiki 底图 + Looper 局部覆盖 Prompt：增量知识合并原型
- 这份 Prompt 已经实际演示了用户想要的“局部新增/替换更新”思路：Kiki 是 `BASE_GRAPH`，Looper 不是第二棵完整树，而是 `LOOPER_OVERLAY`，只有明确 trigger 才插入、细化或覆盖局部动作；`GLOBAL_GUARD` 永远高于两者。
- 它定义了冲突优先级 `GLOBAL_GUARD > 已激活覆盖层 > BASE_GRAPH`，并对含糊拒绝、混合忙闲、明确意愿、加微信时机、回拨/再触达、二次触达、真实性分别写了 P1–P7 的覆盖/依赖规则。这是目前最接近“知识更新决策”的沉淀。
- Looper 覆盖项已呈现多种更新类型：前置硬门槛（插入新 gate）、拒绝原因探询（插入中间节点）、混合忙闲（改变状态更新逻辑）、明确意愿时先展示资源（改变动作顺序）、联系方式触发（新增 guard）、二次触达直接资源（替换基础动作）、公司标签对齐（新增可选观察）。
- 当前合并仍是人工完成：Prompt 没有保留每个 overlay 变更的候选来源、支持证据条目、与旧规则的语义 diff、审批记录或生效版本；只能从最终文本倒推为什么覆盖。
- 统一策略分的口径很清晰：所有适用的 BASE/OVERLAY/GUARD 原子规则进入同一分子和分母，不分 Kiki 分、Looper 分；但规则结果可标明来源层。这可作为最终评价产品的策略层输出原则。
- 输入契约进一步证明评价器依赖多源数据：客户硬门槛、完整资源清单、真实身份/授权、历史触达、CRM/平台日志、公开事实。单纯“导入交流记录”只能支撑策略/话术抽取和部分电话内评价，不能支撑完整真实性与前置匹配评价。
- 覆盖层原子规则也已按与 BASE 相同的字段体系编译，并新增 `strategy_layer` 与 `overlay_activations`。这意味着未来 Prompt 生成器可以从统一规则 schema 编译 BASE、OVERLAY、GUARD，而不必维护三种互不兼容文本模板。
- GLOBAL_GUARD 目前至少三类：身份真实性、岗位/客户/访谈/连接等资源真实性、人物/团队/新闻/候选人个人事实不编造；每类都遵循“有外部事实才 PASS/FAIL，无事实为 NA + 缺口”。
- 覆盖层不全是计分规则：候选人质量/岗位匹配拆分、职级适配核实、公司标签对齐、信息来源纪律、动态状态感知可作为 `optional_observations`。因此知识条目需要区分 `mandatory_rule`、`optional_observation`、`internal_reasoning_model`，不能一律变成评分分母。
- 完整输出 schema 已显式容纳 `overlay_activations`、`strategy_layer`、`unscored_unknowns`；这是差异型知识运行的好基础。但 Prompt 仍缺少“当前知识版本、每个覆盖规则由哪条交流证据/哪次审核产生、何时替代旧规则”的 provenance 字段。

## 2026-08-12｜Looper 系统级稿：前半部分的产品范围
- 电话评价产品不能只优化“加微信”：Looper 的一级业务骨架是寻访 → 转换 → 推荐 → 面试 → Offer，通话同时生产业务结果和候选人/市场数据；后续推荐、面试、Offer 应持续回写并校准知识。
- Looper 区分规模型高频执行与深度型拿线索—推理—再提问。未来 Agent 产品至少需要“稳定流程执行器”和“动态线索推理器”两种能力，不能用一份固定话术 Prompt 包打天下。
- 匹配不是一个总分，而是至少五个对象：候选人质量、客户商业门槛、候选人—岗位关系、候选人—公司关系、可落地性。职级推断还需置信度/证据/例外/待核实字段；技术栈要下钻到业务场景和实际问题。
- 这与本轮产品形成强耦合：新交流记录不只会产生“话术更新”，也可能补充公司标签、客户门槛、职级映射、候选人诉求、匹配判断和下次核实问题。知识更新引擎必须允许不同知识域，而不只维护电话树。
- 二次通话应建模为“首次基础能力 + 历史状态 + 新时间点状态 + 节点替换/更短路径”，同时分清本通停止与未来再激活。上次联系时间、原因、约定、介绍资源、候选人诉求、尝试次数等都是运行态，不是静态策略节点。
- Looper 明确留下大量未知：推荐/面试/Offer 子流程、触达最大次数/冷却周期/永久停联、匹配量化方式等。产品必须保留 `[?]` 和未定义状态，不能把讨论稿自动编译成“完整真理”。

## 2026-08-12｜Looper 系统级稿：知识库与闭环
- 知识域已被讨论稿拆为七类实体库：客户/合同、公司—业务线—团队、岗位、候选人、市场事件、互动记忆、结果反馈；大型公司必须细到业务线/团队，不能只用公司级标签。
- 每条知识都需要证据元数据：来源类型、原始证据、采集/更新时间、适用实体/范围、事实/经验/推测、置信度、敏感级别、能否用于对外话术、冲突来源与版本。这与本轮“新交流记录能否新增/替换旧内容”的判断直接对应。
- 知识库需要保存关系，不只是标签：公司→业务线→团队→岗位，候选人→经历/诉求，候选人↔岗位/公司适配，客户规则约束岗位/人群，事件影响实体/意愿，历史互动更新状态，结果校准规则。
- 完整学习闭环已明确为：知识 → 匹配 → 触达 → 获得新证据 → 更新知识与匹配；推荐/面试/Offer 结果再校准判断规则。用户本轮提出的“导入交流记录 → 对比旧体系 → 更新 → 重生评价 Prompt”可以视为这个闭环中“新证据 → 知识/规则升级”的专门产品化。
- 现稿仍建议先拆清匹配对象与知识最小实体，再写最终 Prompt/Schema；这与当前用户希望先详聊细节、暂不立刻实现的节奏一致。

## 2026-08-12｜Top v0.2：Kiki 对端到端系统的增量
- v0.2 在知识/判断/触达/流程/回写之间新增“触达简报层”：每次呼出前生成为什么找、主岗位、最强真实切入点、待核实信息、本通目标、后手资源。这是从匹配结果到电话策略执行之间缺失的中间产物。
- Kiki 增加“通话深度自适应”：积极且有时间可一通聊深；观望或时间不足先建立联系方式资产再约；当前不方便优先约回拨。联系方式被建模为平台账号、真实号码、微信与渠道许可，不只是一个转化布尔值。
- Kiki 强化匹配输出里的主岗位/主抓手/后手资源和“偏好原因”。上游匹配不能只输出岗位列表；还要解释为何选主岗位、抓手与候选人真实交集、主岗位失败后允许调用什么真实资源。
- 再次触达被分为已约回拨、新资源验证、软拒绝再激活、强拒绝/停止四类。历史状态必须记录渠道、已用话题/岗位/价值点、候选人许可与风险信号；高频案例仅能证明要记历史，不能直接变成频控规则。
- 以上增量进一步说明：交流记录提炼 Agent 的输出不应只有“新节点/新话术”，还应能产出触达简报字段、联系方式资产更新、互动记忆更新、知识/关系资源条目和治理风险。

## 2026-08-12｜Top v0.2：共享系统与独立策略边界
- v0.2 扩展到八类知识实体，新增“关系资源与服务能力库”；岗位/团队事实、人物关系、服务能力、候选人偏好原因只有在真实、可追溯、当前可用时才能进入触达简报。
- 两位猎头可融合的是系统级数据对象和长链路接口：知识/关系资源、多维匹配、触达简报、联系方式/互动记忆、推荐/面试/Offer、结果回写与治理。

- 由此推导未来知识更新的作用域至少要有 `shared_system_knowledge`、`strategy_module(kiki/looper/other)`、`evaluation_policy` 三层。一次新资料可以只更新某个猎头的局部策略，也可以提出共享知识；两者审批和发布不应混在一起。
- 当前证据索引已经能定位到来源人、主题和时间段，是 provenance 的人工版本；产品化时应升级为每个知识条目/规则/话术模板都带可点击原文证据，而不是只在文档末尾放全局索引。

## 2026-08-12｜Kiki/Looper 策略手册：知识中间层

- Looper v2 对 50 个映射项做了证据分类：13 个有直接话术、2 个部分话术、34 个仅策略说明、1 个状态条件。这个分类就是未来交流记录抽取后的第一道“可编译性判定”：策略事实不等于可直接生成候选人话术。

- 人类可读 Word 手册可以由结构化知识派生；但若把 Word 本身当唯一真源，难以可靠进行节点/边/话术/证据级 diff，也无法自动重编译多个 Prompt。

## 2026-08-12｜阶段 E 产品化前置理解结论
- 项目已完成高质量但主要依赖人工的“原始交流证据 → 策略结构 → 节点原话 → Graph/Overlay → 评价规则 → Agent Prompt”链路；要做的不是从零写一个更长 Prompt，而是把这条知识生产与发布链变成可持续运行的产品。
- 建议目标闭环为：导入交流记录及上下文 → 说话人/证据抽取 → 策略、节点、边、guard、话术分层建模 → 与已批准基线做语义 diff → 给出 add/modify/deprecate/replace/override/reclassify/split/merge 变更提案 → 人工审阅 → 发布新知识版本 → 编译新版评价 Prompt → 历史 case 回归。
- `Kiki BASE_GRAPH + Looper activated OVERLAY + GLOBAL_GUARD` 是当前最接近未来发布模型的原型；但 Looper 不能被强补成完整电话树，应允许策略 fragment/overlay 独立存在。
- Prompt 应被视为结构化知识和评价政策的编译产物，而不宜继续作为唯一知识真源；否则证据追溯、局部更新、版本 diff、多 Prompt 派生和回归验证都会很脆弱。
- 产品第一阶段最需要用户参与定义的不是 UI，而是：允许哪些输入与上下文、何为值得更新的新证据、哪些变更必须人工批准、知识对象最小 schema、BASE/OVERLAY/GUARD 的作用域与冲突优先级、Prompt 发布前的回归门槛。

## 2026-08-12｜飞书标准 TXT 样本核对
- 用户提供 `C:\项目7.20始\looper学习2.txt` 作为标准输入样本；文件约 110 KB、1764 行，结构为会议日期/开始时间/总时长 → 关键词 → `文字记录:` → 说话人+时间戳与正文块。

- 时间戳在一小时内使用 `MM:SS`，超过一小时后使用 `H:MM:SS`，解析器须同时兼容。
- 同一会议会播放或讨论电话 case，导致会议参与人和被播放电话角色共存。角色分层不能仅依据说话人标签，需要语境识别和必要时人工消歧。

## 2026-08-12｜说话人确认方案修正
- 用户澄清固定业务场景：访谈只学习 Looper 等指定 Top 猎头的想法和策略，其他人只是提出问题或提供引子；无需逐一审核所有人的角色。

- 只有目标专家发言可成为候选策略证据，其他发言只保留为理解专家回答所需的上下文。
- 真正需要重点治理的是目标专家发言的证据性质，而非所有说话人的身份：需区分明确策略、具体 case 条件判断、假设回应、转述、直接话术和证据不足内容。

## 2026-08-12｜策略/话术层级与跨专家局部最优
- 用户明确：策略与话术必须分层。策略是猎头行为节点、候选人反应/状态条件边和触发结构；可为 Kiki 式完整路由 Graph，也可为 Looper 式局部触发 fragment。
- 话术是策略节点的下一层具体语言行为，至少拆为段落功能及排列、句子内句法顺序/句式、具体用词与语感；还需解释表达功能，并可单独提出更适合 AI 的候选表达。
- 完整 Graph/局部 fragment 描述结构覆盖范围，不等于通用策略/具体 case 条件性策略。后两者描述适用范围；专家主动陈述、假设回应、case 推理、转述等描述证据语境，应分别标注。
- 之前建议的六类扁平证据分类被撤回，改为多轴模型：知识层级、结构覆盖、适用范围、证据语境、审核状态。
- 用户提出关键跨专家风险：专家 A/B 可能分别处在不同的策略局部最优，体系各自自洽，强行融合需要跨越效果低谷并可能降低表现。产品必须允许并行独立体系，融合只能是经兼容性和效果验证后的选择，不是默认目标。

## 2026-08-12｜泛化状态与专家访谈学习闭环

## 2026-08-12｜评价标准选择机制与融合问题拆分
- 用户确认：下游实际评价时，由人手动选择本次采用哪位猎头克隆出的策略话术组；公司 AI 猎头不与某位专家永久绑定，系统也不根据被评价电话自动猜测标准。
- `expert` 是证据来源；`专家策略话术组` 是已批准、可版本化的知识组合；`发布包` 是该组合的下游交付版本；一次评价任务只需记录本次选择的发布包 ID/版本。
- “本次选哪一整组”与“多专家内容能否融合”是孪生但独立的问题：前者是运行时选择机制，已经确定；后者是知识生产和验证问题，仍需讨论。

- 若未来允许融合，较稳妥的候选方向是：先将融合结果作为新组独立命名、审核、版本化和回归，再进入可选发布包；不能在评价运行时临时拼接。该方向尚未确认为需求。
- 用户随后确认该 MVP 边界：首版只整套选择已批准的 Kiki、Looper 或其他专家策略话术组，不提供跨专家临时拼装，也不做融合判断。
- 跨专家兼容性与局部最优融合移至后续阶段；未来融合结果必须作为新的独立策略话术组，经过人工审核、版本化和历史 case 回归后才可发布。
- 用户确认同一专家的组关系先按保守规则设计：默认一位专家维护一套策略话术组；只有人工明确认定存在目标、前提或运行逻辑不同且各自自洽的打法时，才拆为多套独立组。
- 系统可以从新访谈中提出“更新既有组”或“新建一组”，但不能静默拆组；不同组需要独立选择、审核和版本化。

## 2026-08-13｜基线不可变与独立平台边界
- 用户确认已批准的知识基线、策略话术组版本和评价规则发布包版本不可直接改写；新访谈只能产生候选知识/变更提案，人工批准后生成新版本。
- 用户确认本产品后续单独建设独立平台，不集成 Mentor 的 EVALLAB/评估平台。知识生产、审核、版本管理和 Prompt 编译/发布包生成在本平台完成。
- 外部评估平台只是发布包的消费方；MVP 通过人工复制、下载、导出或文件交付，不由本产品调用其 API、自动发布或写入外部评价任务。
- 回归验证必须不依赖 EVALLAB；执行方式（本平台内置、人工外部执行后上传等）仍是开放设计问题。

## 2026-08-13｜Schema 讨论：持续完善的策略体系（待确认）
- 用户指出：Looper 的大量 fragment 不应直接被解释为“Looper 的最终策略本来就是碎片化”。更合理的解释是，访谈资料和提问结构尚未覆盖完整体系，同时 Looper 的实际打法可能比 Kiki 更复杂；只要真人能够完整打完电话，就应存在尚未被我们充分提炼出的链路。
- 因此，Graph 与 Fragment 的共存首先是知识建设过程中的整合状态：Graph 表示当前已连接的主结构；Fragment 表示已有证据支持、但尚未连接到主结构或尚未找到连接条件的局部知识。目标是持续补访、分析和连接，但不预设所有内容必须最终变成单一路径或单棵树。
- 完整度、结构整合状态和审核/发布状态应分开记录。Fragment 可以已经被确认真实存在，但仍未连接；已连接的 Graph 也可能存在未覆盖分支或证据不足。
- 用户对 Overlay 的含义尚未确认。当前候选定义：Overlay 不是未连接碎片，而是基于某个已存在基线、在明确阶段/条件下增加、替换或限制节点/边的“叠加变体层”。倾向先不把 Overlay 作为 MVP 核心结构类型，等出现真实案例再正式定义。
- 用户提出的长期路线：先独立保存并版本化各专家策略话术组，再建立跨专家对比/对齐/冲突分析空间，生成独立的融合候选组。源专家组不被反向改写，融合组须独立审核、版本化和回归。
- 话术融合应分层处理：相同功能结构可抽象为共同模板；不同句法/用词保留为带来源的替代变体；AI 综合表达必须标注为生成候选，不得伪装成任何专家原话。正例、反例和替代表达可作为 Prompt 的可选示例，但不自动成为策略事实。

## 2026-08-13｜Overlay 纳入 MVP，但采用轻量定义
- 用户确认 Overlay 也要在 MVP 中先支持记录，因为同一专家的第二次访谈可能直接补充相对于既有基线的阶段/条件性变体。
- MVP 对 Overlay 只要求可保存、追溯、审核并随策略话术组版本发布；至少关联明确基线、触发/适用范围、作用位置、变更操作、证据和审核状态。
- 不要求首版实现复杂 Overlay 引擎（自动优先级、冲突合成、嵌套、跨组组合、自动回退）；评价时仍不选择 Overlay 零件，是否纳入由更新、审核和发布版本决定。
- 之前“Overlay 后置、只保留 Graph+Fragment”的候选建议已被本次用户决定替代。Graph、Fragment、Overlay 都进入 MVP，但语义必须保持区分。

## 2026-08-13｜Overlay 轻量语义收紧（v0.20）
- Overlay 不是访谈文本中脱离基线独立抽出的第三种“碎片”；它必须相对一个明确、可追溯的既有基线提出。后续访谈/新增证据先生成 Overlay 候选，审核并发布新版本后才生效。
- 没有明确基线时，不命名为 Overlay，按 Fragment 或普通结构变更保存，避免模型凭常识补出叠加关系。
- 完整度报告把 Overlay 作为“基线变化/叠加候选”单列，记录证据与待审核状态，不用 Overlay 数量评价体系完整度。
- 发布包只编译已批准且具备编译资格的 Overlay；复杂优先级、冲突、回退、嵌套和跨组组合仍是后续议题。
- “纳入 MVP”具体指：能生成候选、展示基线→候选差异、进入审核，并在批准后写入新组/发布包版本；不要求在评价运行时实现动态 Overlay 解释器。
- MVP 的 `base_ref` 只能指向同一专家策略话术组的已批准基线；跨专家或跨组 Overlay 组合仍属于后续能力，不得借 Overlay 绕过“不临时融合”的边界。

## 2026-09-01｜边审核语义与 Graph 展示稳定性发现

- `condition_review_status=confirmed` 是单边人工保存事实，不是来源节点全部路由已消歧的证明。同源同条件异目标必须作为冲突组继续阻断，否则电话模型无法判断具体走向。
- 问题总数不足以支持人工审核。一个重复条件冲突组可能包含两条或更多红边，界面必须同时展示来源、条件、全部目标及逐边入口；仅靠图上颜色会在密集 Graph 中丢失定位信息。
- Graph 展示稳定性至少有四个身份维度：任务/候选 Graph、物化 Graph 哈希、布局画像哈希、浏览器布局模式。未固定这些身份时比较两张截图没有意义。
- 算法输出确定性、布局缓存命中和浏览器最终可读性是三件不同的事。现有单元回归只能证明第一层；缓存/降级、人工坐标恢复、缩放和密集边交叉仍需独立使用级测试。
- 展示失败不能改变策略 Graph 或 Prompt，但会直接妨碍人工发现问题边，因此 Graph 可读性属于审核质量风险，而不是纯美术问题。
