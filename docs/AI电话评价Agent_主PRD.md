## 1. 产品概述

### 1.1 产品暂定名称

Top 猎头行为克隆知识与双 Prompt 编译系统

### 1.2 已确认的产品目标

将目前由人工完成的以下链路产品化。当前阶段首先以“忠实克隆一位 Top 猎头明确表达和演示的电话行为体系”为目标：通过访谈获得该专家在不同候选人状态/反应下会采取什么行动、为何采取、具体如何表达，再将其结构化为可追溯、可审核、可版本化的专家克隆 Graph。策略结构提炼、话术映射和 Prompt 生成借助大语言模型（LLM）的语义理解能力完成，但所有 LLM 产出均为候选提案，不自动批准或发布：

`导入专家访谈记录及上下文 → LLM 辅助识别说话人与证据 → LLM 辅助提炼专家克隆 Graph（猎头行为节点/候选人状态与反应触发边/节点话术）→ 与已批准基线做语义对比 → 生成变更提案 → 人工审核 → 发布新知识版本 → 基于同一已批准克隆 Graph 分别编译电话执行 Prompt 与评价 Agent Prompt → 用测试或历史 case 回归验证`

本产品调用的大语言模型通过可配置的、OpenAI Chat Completions 兼容的 LLM API 模块接入（见 4.11 节 OPEN-P0-13），不得把产品逻辑绑定到某一家供应商或某个模型名。LLM 用于理解、提炼和生成，不用于自动决策；所有知识状态变更和发布必须经过人工 Gate。

本产品的业务范围仅覆盖电话沟通策略及其评价规则。

### 1.3 已确认的知识治理原则

1. Prompt 是结构化知识和评价政策的编译产物，不是唯一知识真源。
2. “专家说过”不等于“允许上线”；高风险策略可保留为证据，但须由 Guard 或人工审核决定是否启用。
3. Kiki、Looper 等猎头的电话策略独立保存，不虚构统一的“Top 猎头人格”。
4. 已连接策略 Graph、尚未充分连接的局部 Fragment，以及相对于明确基线的 Overlay 都是一等知识对象；三者语义不同。Fragment 不代表专家最终是“碎片化风格”，Overlay 也不等同于 Fragment。
5. 策略节点存在，不代表存在可直接使用的真人话术。
6. 每次变更都必须能追溯：来源人、原始位置、上下文、变更原因及受影响的评价项。
7. 策略与话术是两个不同层级的知识对象，不得混为同一类抽取结果或评价规则。
8. 访谈记录中的信息是散碎的、口语化的，不能通过规则直接提取为结构化的策略流程图和话术；必须借助 LLM 的语义理解能力完成提炼和映射。但 LLM 的所有产出均为候选提案，不替代人工审核决策。
9. 最终从同一专家克隆 Graph 编译电话执行 Prompt 和评价 Prompt；评价 Prompt 再分为策略流程评价和话术评价两种，分别以策略流程图和节点话术为规则标准。
10. 当前阶段以“先克隆、后优化”为原则。专家克隆知识只描述目标专家本人明确表达、演示或明确认可的做法；AI 优化建议、公司规范性 Guard 和未来跨专家融合均为独立派生层，不得覆盖或伪装成专家原始克隆知识。
11. 同一已批准专家克隆 Graph 是下游电话执行 Prompt 与评价 Prompt 的共同知识基线：执行 Prompt 指导电话模型尽量按该专家的条件反应、动作和表达运行；评价 Prompt 判断实际电话轨迹与表达和该专家基线的符合程度。两类 Prompt 用途不同，不得混成一份含糊的提示词。
12. 当前专家克隆证据主要来自对 Top 猎头的访谈、讨论和现场模拟，不默认存在专家真实工作通话录音。因此系统只能声明“符合专家在访谈中明确表达或演示的做法”，不得无证据声称已完整复现其真实工作行为或业务效果。

## 2. 产品愿景与阶段范围

### 2.1 完整产品愿景

面向公司内部产品与运营人员，将其与 Top 猎头访谈后获得的交流记录及上下文，转化为可追溯、可审核、可版本化的独立专家克隆 Graph，并据此分别编译可供电话模型使用的执行 Prompt，以及可供下游评估 Agent 使用的评价 Prompt。

本产品本身作为独立的内部平台建设和运行，不并入 Mentor 的评估平台或电话运行平台。知识生产、变更审核、版本管理、双 Prompt 编译和发布包生成在本平台内闭环；对外仅通过人工导出/复制或文件交付，电话模型和下游评估平台分别是执行 Prompt 与评价 Prompt 发布包的外部使用方。

### 2.2 当前 MVP 范围

- `SCP-001`【已确认】MVP 服务公司内部产品/运营人员，可在其与 Top 猎头完成访谈或讨论后进入本工作流。
- `SCP-002`【已确认】MVP 覆盖：资料导入、证据识别、策略结构化、基线语义对比、变更提案、人工审核、知识版本发布，以及基于同一已批准专家克隆 Graph 的电话执行 Prompt 与评价 Prompt 编译。其中 Overlay 的 MVP 支持仅要求从新访谈/新增证据相对明确基线生成候选、展示基线与候选差异、进入审核，并在批准后写入新的组版本/发布包；不要求电话或评价运行时实现动态 Overlay 解释器或复杂叠加引擎。
- `SCP-003`【已确认】MVP 的责任终点是形成经过审核、可人工交付给电话模型使用方和外部评价使用方的双 Prompt 发布包；本产品不直接承担真实电话执行或真实电话评分。
- `SCP-004`【已确认】MVP 不读取公司真实 AI 猎头呼出记录并执行质量评分；该职责属于下游评估 Agent/平台。
- `SCP-005`【已确认】MVP 以独立平台形式提供知识更新、审核、版本发布和 Prompt 编译能力，不要求接入、嵌入或合并部署到 Mentor 的评估平台。
- 待讨论：首版具体输入格式、输出发布包、人工确认点和验收门槛。

### 2.3 后续阶段

- `FUT-001`【不纳入本产品】与下游平台的 API 同步、自动发布、发布回执和结果回流；如果未来需要，另立跨平台项目并重新评审，不属于本产品当前路线。
- `FUT-002`【候选方向】通过人工导入或文件交付接收真实评价结果、专家复核结果或业务结果，回流校准知识和规则；不预设与外部平台的自动接口。
- `FUT-003`【候选方向】支持跨专家兼容性判断和组合策略话术组生产；组合结果只有经过独立命名、人工审核、版本化和历史 case 回归后，才可成为新的可选执行与评价标准。
- 以上仅为未来方向，不作为 MVP 成立或验收的前置条件。

## 3. 用户与使用场景

### 3.1 主要用户

- `USR-001`【已确认】公司内部产品/运营人员：与 Top 猎头讨论后发起知识更新任务，查看系统提炼结果，参与或组织审核，并取得新版评价 Prompt。

### 3.2 相关角色

- Top 猎头：知识与证据来源，当前不默认要求其直接操作系统。
- 策略复核者/发布批准者：负责裁决是否更新知识和评价标准；具体由谁承担、是否需要多人审批，待讨论。
- Mentor/评估平台负责人：下游评价规则消费者或协作方，不是本独立平台的日常操作者，也不是本产品的部署宿主。

### 3.3 核心使用场景

产品/运营人员完成一次 Top 猎头访谈后，创建一次策略更新任务并导入材料；系统将专家口述或模拟的“候选人状态/反应 → 猎头动作 → 专家示范表达”提炼为候选克隆 Graph，展示新证据、旧基线、差异和影响，协助人工决定是否更新；批准后发布新知识版本并分别编译可交付的电话执行 Prompt 与评价 Prompt。

## 4. 需求清单

> 需求 ID、状态和验收标准将在讨论过程中逐项补齐。

### 4.1 交流记录与上下文导入

- `IN-001`【已确认】MVP 采用单入口输入：用户开始一次知识更新任务时，只需导入一份交流记录文本，不要求先填写完整资料表或同时上传其他附件。
- `IN-002`【已确认】系统必须先完整解析交流记录，再自动提取并预填任务元数据，包括会议时间、参与人、Top 猎头身份和说话人角色等可从原文获得的信息。
- `IN-003`【已确认】自动预填字段必须保留其原文来源位置，允许用户查看和纠正；缺失、冲突或无法可靠判断的必要字段，再由系统要求人工补录或确认。
- `IN-004`【已确认】候选人画像、岗位 JD 及其他访谈上下文如已包含在交流记录中，应从文本中提取并与相关证据绑定；MVP 不强制用户额外上传这些附件。
- `IN-005`【已确认】MVP 首版输入格式为飞书会议导出的标准 `.txt` 文件；首版不要求支持 DOCX、粘贴文本或其他转写格式。
- `IN-006`【已确认】解析器应识别标准 TXT 中的会议日期与开始时间、会议时长、关键词区、`文字记录:` 起始标记、说话人标签、发言时间戳和发言正文。
- `IN-007`【已确认】发言时间戳须同时支持 `MM:SS` 与 `H:MM:SS`；正文范围从当前发言头延续至下一个发言头。
- `IN-008`【已确认】必须原样保留实名和匿名说话人标签，不得因名称相似或编号连续自动合并说话人。
- `IN-009`【已确认】导入后须保留原始 TXT、原始发言顺序、时间戳及可定位到原文的引用信息；后续所有抽取结果均由这些原始证据派生。
- `IN-010`【已确认】系统不需要逐一识别或审核所有非目标说话人的业务角色；只需识别本次要学习的目标 Top 猎头。其他说话人的发言保留为问题、引子和上下文。
- `IN-011`【已确认】普通重复上传仍按内容哈希命中既有不可变来源，不覆盖旧快照或旧任务；用户可显式选择“从当前来源新建重跑任务”。重跑任务须生成新的 task/source 实例并从 G0 开始，不继承旧目标专家、基线选择、Gate、证据审核、候选知识、分析运行、编译或发布状态；可复制旧任务下不可变 Graph 基线供新 G1 重新选择，并保留原任务、原来源和原基线引用。

### 4.2 说话人、证据与信息层级识别

- `SPK-001`【已确认】系统解析 TXT 后，自动识别本次要学习的目标 Top 猎头，并给出识别置信度及判断依据。
- `SPK-002`【已确认】目标专家识别为高置信度且不存在冲突时，系统自动进入下一步，不设置固定人工确认 Gate。
- `SPK-003`【已确认】目标专家识别为低置信度、存在多个合理候选人或信息冲突时，系统暂停并要求产品/运营人员人工选择或补录目标专家。
- `SPK-004`【已确认】需要人工确认时，界面展示候选说话人标签、代表性原文、发言数量、时间戳范围、系统判断依据和置信度。
- `SPK-005`【已确认】只有目标专家本人的发言可进入“候选策略证据”集合；其他人的发言只作为提问、引子和上下文，不得独立形成该专家的策略、节点、线路或话术知识。
- `SPK-006`【已确认】无论自动通过还是人工纠正，最终目标专家、系统初始判断、置信度、确认方式和人工修改均须写入任务审计记录。
- `SPK-007`【待讨论】目标专家发言还需进一步区分明确策略、具体 case 条件判断、假设回应、转述他人、直接话术和证据不足内容；分类规则、置信度和人工复核位置待后续确定。
- `SPK-008`【已确认】G1 的结果必须落为本任务可校验的目标说话人标识集合（如稳定 speaker ID，并保留原始标签/别名），不能只保存一个用于提示词展示的自由文本名称。目标专家被重新选择后，旧目标专家派生的候选证据、分析运行和未发布知识不得静默沿用，须失效、重算或进入人工迁移复核。
- `SPK-009`【已确认】其他人的发言可以作为上下文，但不能单独满足知识对象的目标专家证据门槛。每个候选策略、节点、边、触发器和话术至少须直接回链一条目标专家发言；上下文引用须与支持性证据分字段记录，不能混在同一列表中冒充专家证据。
- `SPK-010`【已确认】“目标专家明确认可他人提出的策略”可形成独立的 endorsement 候选，但必须同时记录目标专家本人的明确认可发言、被认可内容的上下文引用和认可关系；被认可内容不得伪装为目标专家直接原话或 direct_script。孤立的“对、嗯、是”等承接词在无法唯一对齐被认可内容时证据不足，不能自动形成策略；是否升级为可复用规则仍按 `OPEN-P1-02` 复核。
- `SPK-011`【已确认】目标专家归属是服务端不变量，而非提示词建议。系统至少在 LLM 分类/结构结果写入、知识对象创建、G3 批准三个位置校验证据是否属于当前任务及当前目标专家；任一层失败均返回结构化阻断，不得仅依赖模型遵守指令。
- `SPK-012`【已确认】“其他人只作上下文”要求策略提炼保留必要上下文窗口：目标专家发言、其所回应的问题/建议及相邻发言使用独立引用传入模型。系统不得为了筛出目标专家而删除理解明确认可、反对、转述或条件回答所需的上下文，也不得把上下文直接提升为支持性证据。
- `SPK-013`【已确认】解析层的原始 `utterance` 不是可批准的 `evidence_kind`。进入 G2 前必须归为 `strategy`、`script`、`context` 或 `meta` 之一，并记录是否具备目标专家证据资格；未分类、分类值非法或目标归属未决时不得批量批准。已批准证据不得被 LLM 原地覆盖；重分析产生新的候选分类/版本和差异，交由人工复核。

### 4.3 策略、节点、边、Guard 与话术抽取

#### 4.3.1 策略层

- `KNW-S-001`【已确认】策略描述电话中的行动结构，由猎头行为节点、候选人反应/状态、连接节点的边、触发条件和必要的 Guard 构成。策略结构的提炼借助 LLM 从散碎的访谈发言中理解并梳理出节点、边和路径，形成候选 Graph/Fragment 供人工审核。
- `KNW-S-002`【已确认】策略节点必须表示猎头的可观察行为；候选人的反应、状态或条件用于定义边和触发器，不与猎头行为混作同类节点。
- `KNW-S-003`【已确认】当前证据已经明确连接的一组猎头行为节点、候选人状态/反应条件与边，可记录为已连接 Graph。Graph 只表示当前已知范围内的连通性，不证明专家整体策略已经覆盖，也不要求呈现为单一路径或完整树。
- `KNW-S-004`【已确认】当前证据支持、但与周边策略的连接尚未知、未证实或未批准的局部对象，记录为 Fragment；该形态适用于任何专家，不代表专家最终是“Fragment 型”。后续访谈可通过有证据的 `link/attach/merge` 变更将 Fragment 挂接或合并到更大的 Graph；不得凭常识自动补边。
- `KNW-S-005`【已确认】MVP 支持在已有明确、可追溯基线时，由后续访谈或新增证据相对该基线提出 Overlay 候选；MVP 中基线必须属于同一专家策略话术组及其已批准版本。候选先进入变更提案，未经审核和版本发布不得自动生效。Overlay 是相对于一个基线/版本，在特定触发条件或适用范围下，对节点、边、线路或 Guard 进行增加、细化、替换、限制或抑制的叠加对象。至少记录基线引用、作用范围/触发条件、变更内容、证据来源和审核状态；若没有明确基线，应记录为 Fragment 或普通结构变更，不得仅凭模型推断命名为 Overlay。MVP 不要求自动解决复杂优先级、冲突合成、回退、嵌套或跨组组合。
- `KNW-S-006`【已确认】Graph、Fragment、Overlay 是否纳入某个策略话术组版本，在知识更新、变更审核和版本发布时决定；评价运行时不允许操作人员临时选择或拼装这些零件，只能整套选择已发布的策略话术组/评价规则发布包。
- `KNW-S-007`【待讨论】Overlay 的详细优先级、冲突处理、未触发时的回退行为、可否嵌套及其跨专家使用范围，待出现真实案例后定义。
- `KNW-S-008`【已确认】当前克隆知识主要来自专家访谈中的口述条件、假设回答和现场模拟，不默认来自真实工作通话。访谈中“候选人说/表现/处于某种状态时怎么办”所描述的候选人侧信息，原则上提炼为边的触发条件、入口条件或必要的 Guard；专家随后明确表示会执行的反应提炼为猎头行为节点。不得把访谈者提出的假设本身误写成目标专家事实，也不得把候选人状态混作猎头行为节点。
- `KNW-S-009`【已确认】一条触发边必须至少由目标专家对该情境的明确回答、演示或明确认可支持；访谈者的问题只作为 `context_refs` 帮助解释条件。对于访谈未说明的真实通话细节、前后步骤、候选人结果或专家临场选择，不得凭常识补齐；连接未知时保留 Fragment、未知触发器或自由裁量项。

#### 4.3.2 话术层

- `KNW-U-001`【已确认】话术位于策略节点的下一层，描述完成该猎头行为节点时具体如何说；话术不等同于节点或策略线路。话术映射借助 LLM 将专家原话定位到策略节点，并判断"有直接话术/部分话术/仅策略说明/无节点话术"，形成候选话术对象供人工审核。
- `KNW-U-002`【已确认】话术至少按三层拆解：
  1. 段落内功能结构：包含哪些句子功能，以及这些功能的排列顺序。
  2. 句子内句法结构：信息和成分的语法顺序、句式与表达骨架。
  3. 用词与语感：具体措辞、语气、自然度和风格。
- `KNW-U-003`【已确认】话术抽取还应解释表达的具体含义与功能，并允许在保留真人证据的同时，提出更适合 AI 执行的候选表达；真人原话与 AI 优化建议必须分开保存和审核。
- `KNW-U-004`【已确认】策略节点存在不代表存在可学习的直接话术；缺少直接语言证据时，系统不得伪造真人话术。
- `KNW-U-005`【已确认】策略层变更与话术层变更分别比较、分别审阅，并在最终评价规则中避免对同一问题重复扣分。
- `KNW-U-006`【已确认】在产品语义和 Graph 展示中，话术属于对应猎头行为节点；在底层 schema 中可作为节点下带稳定 ID、版本和证据引用的独立 `script` 对象保存，以支持一节点多种表达、独立审核和可追溯更新。该技术拆分不改变“统一专家克隆 Graph 同时包含策略与话术”的产品事实。
- `KNW-U-007`【已确认】必须区分三类文本：①目标专家在访谈中的完整原始发言；②目标专家明确示范自己会对候选人说出的 `direct_script` 原话 span；③由 AI 或人工提出的优化/改写表达。只有第二类可作为专家示范话术；“我会先问他什么时候方便”等策略说明不得伪装成直接话术，第三类不得进入纯克隆层或覆盖第一、第二类证据。

#### 4.3.3 互相独立的知识标注轴

抽取结果不得使用一组互斥标签同时承担不同概念。至少分开记录：

1. `knowledge_layer`：策略 / 话术。
2. `representation_form`（策略）：已连接 Graph / Fragment。
3. `coverage_scope`（策略）：局部触发、阶段子图、端到端等覆盖范围；具体枚举待细化。
4. `linkage_status`（策略）：未连接、部分连接、已连接；它描述知识当前的连接状态，不描述专家最终风格。
5. `applicability_scope`：通用、条件适用、单一 case 观察、范围待确认。
6. `evidence_context`：专家主动陈述、回答访谈假设、基于具体 case 推理、转述他人、直接示范话术等。
7. `review_status`：候选、待确认、已批准、已拒绝、仅存档、已废弃。
8. `compile_eligibility`：是否允许进入某个已发布 Prompt，由证据、适用范围和人工审核独立决定，不得由 Graph/Fragment 形态自动推断。

Overlay 不作为 `representation_form` 的一个值，而作为相对于基线的独立叠加对象，至少关联 `base_ref`、触发/适用范围、作用位置、变更操作、证据和审核状态；候选与已批准状态必须分开记录，且不得仅由其“Overlay”名称自动获得编译资格。

- `applicability_scope`【已确认】采用三个泛化状态：
  1. `已确认可复用规则`：专家证据足以支持在明确适用条件下重复使用。
  2. `单 case 候选规律`：当前只由一个具体候选人/岗位/上下文 case 支持，尚不能作为稳定规则发布。
  3. `泛化范围待确认`：看似存在可复用模式，但适用条件、边界或反例尚未问清。

所有策略边本身都可以带触发条件，因此“有条件触发”不等于“只能用于单一 case”。“对访谈者假设的回应”如何升级为可复用规则仍待讨论。

### 4.3.4 复杂、经验型策略的表达

- `KNW-C-001`【已确认】不得以是否形成完整 Graph/完整树判定专家最终策略形态或访谈信息完整度；Fragment 首先表示当前知识连接状态。
- `KNW-C-002`【已确认】同一触发位置可以存在多个候选策略动作；系统需允许保存备选动作集合，而不是强行选成唯一下一节点。
- `KNW-C-003`【讨论中】对于 Looper 式经验型选择，知识模型需要表达已知选择线索、动作优先级、互斥/替代关系和未显式化的专家自由裁量。
- `KNW-C-004`【已确认】专家明确表示存在心情、直觉或临场经验等未显式因素时，可作为原始事实和“自由裁量/未知选择因子”保存，但不得被 AI 补写成确定触发规则。
- `KNW-C-005`【已确认】同一专家内部 Fragment 到 Graph 的有证据连接、挂接或合并，不属于跨专家融合，也不要求新建专家策略话术组；只有目标、前提或运行逻辑确实不同且经人工批准时，才考虑拆组。

### 4.9 专家访谈规划与信息完整度反馈

- `INT-001`【已确认】产品不仅处理一次访谈，还需支持围绕同一 Top 猎头多次、针对性补访，持续完善其独立策略体系。
- `INT-002`【已确认】产品需维护一套“需要收集的信息结构”，用于指导访谈者在访谈前规划问题；该结构描述需要了解的策略/话术信息，不要求专家按固定表达风格回答。
- `INT-003`【已确认】每次访谈转化完成后，系统输出简要的“访谈信息完整度与补访建议报告”。
- `INT-004`【已确认】报告至少回答：本次新增了解了什么、哪些证据足以进入候选知识、哪些关键问题仍未覆盖或证据不足、是否建议再次访谈、若需要则下一次优先问什么。
- `INT-005`【已确认】完整度评价针对“我们对该专家体系的了解程度与可编译程度”，不得评价专家本人策略水平，也不得因当前存在 Fragment、Overlay 或尚未形成完整 Graph 而直接判低分。
- `INT-006`【讨论中】系统可基于该专家当前知识基线、未决变更和信息缺口，生成下一次访谈提纲；提纲是否进入 MVP、是否允许人工编辑及其输出形式待确认。
- `INT-007`【候选维度，产品待讨论】访谈完整度不能先压成一个概念，至少可能包含两个独立判断：
  1. `结构覆盖度`：访谈是否取得了产品定义的“必须信息结构”。该判断必须先由业务定义哪些信息结构是所有电话策略体系都必须取得的，哪些只对特定专家/体系适用。
  2. `体系闭环与自洽度`：在专家已经表达的前提、触发器、节点、备选动作、选择线索和终止条件内，能否完成策略推演，是否存在内部矛盾、断路或无法解释的跳转。
- `INT-008`【已确认】大模型可用于体系闭环与自洽度的首轮推演和问题发现，但其结论只能表示“当前显式知识模型在给定测试场景下是否自洽”，不能证明未被访谈覆盖的结构或分支不存在，也不能替代必须信息结构的业务定义。
- `INT-009`【候选维度】除上述两项外，访谈完整度报告还可分别检查：
  1. 策略结构覆盖：已覆盖的电话阶段、触发场景、Graph、Fragment、已知连接和未连接缺口；另列相对既有基线识别出的 Overlay 候选、证据和待审核状态，不把 Overlay 数量直接当作完整度分数。
  2. 决策解释度：触发条件、备选动作、选择线索、优先级、停止条件和自由裁量项是否问清。
  3. 话术证据覆盖：哪些策略节点有直接话术，以及功能结构、句法和用词证据是否足够。
  4. 泛化证据：可复用规则、单 case 候选规律和待确认范围的分布及缺口。
  5. 矛盾与未知：内部冲突、跨次访谈变化、无法解释的线路和待专家确认项。

上述候选维度与“必须信息结构”的关系、完整度的呈现形式，以及哪一项可决定是否需要补访，归入产品内部后续讨论；本轮 Mentor 只确认上方两问。

### 4.10 独立平台前端工作台与控制契约（OPEN-P0-12，首版已确认·MVP草案）

本产品需要一个与 Mentor/EvalLab 平行的独立网页工作台。它负责让产品/运营人员看懂“原始来源→证据→知识→变更→Prompt/发布包”的背后状态，并控制本产品内的任务与审核流程；不负责承接下游真实电话评分运行时，也不为适配 Mentor 平台而设计接口。

#### 4.10.1 MVP 信息架构

参考用户提供的 EvalLab 页面（左侧导航、中央工作区、卡片式配置、运行日志和结果明细），本产品当前 MVP 采用五个聚焦入口：

1. **工作台**：待处理任务、当前 Gate、最近变更、发布状态和异常提醒。
2. **任务与专家**：导入 TXT、显式干净重跑、目标专家确认、精确 Graph 基线选择及整份访谈增量学习入口。
3. **Graph 审查**：在一张画布中查看候选完整图、现有基线或增量差异；点击节点/边查看结构依据、专家原话与时间位置，并对整张候选图批准或驳回。
4. **Prompt 与发布**：编译预览、编译 manifest、Prompt 差异、回归状态、导出与交付核验。
5. **审计与设置**：Gate/access audit、角色/任务范围、非语义显示设置和受控参数。

逐条“证据审核”不再作为默认导航页面。证据识别、分类和 G2 记录属于后台工程；凡需要人判断的结构变化与节点话术，必须在 Graph 审查页连同证据位置一起呈现，避免用户先机械通读整份转写再看 Graph。

MVP 不复制参考平台的“候选人 Agent/反应类型/评委 Agent/真实评估运行”导航；这些属于下游运行平台或当前不在本产品边界内的配置。

#### 4.10.2 主工作区与显示窗口

每个任务详情页采用“上下文栏 + 主工作区 + 右侧控制/详情栏 + 底部事件流”的稳定骨架：

- **上下文栏**：任务 ID、专家、策略话术组/版本、当前状态、当前 Gate、数据敏感级别、最近更新时间。
- **来源/证据窗口**：默认嵌入 Graph 对象详情；展示原始 TXT 的只读全文证据、说话人/时间戳、当前 span、上下文引用、来源哈希和定位信息。目标专家原话与其他人上下文必须分区，后者不得直接归因给专家。D3 内容默认脱敏，未经授权不展开完整原文。
- **知识/差异窗口**：候选与已批准基线的分层 diff；对象稳定 ID、对象类型、状态、作用域、父版本、证据数量、冲突集和引用关系。当前 MVP 以同一 Graph 画布作为主审核面，并保留结构化对象/详情数据为真源；画布不是两张独立图的并排展示。
- **Prompt/发布预览窗口**：只读 Prompt、规则分区、命中的对象/政策版本、`not_applicable`/`insufficient_evidence` 说明、Prompt 大小、Prompt/manifest SHA-256、回归状态和发布包 manifest。
- **控制/详情窗口**：只显示当前角色和当前状态允许的动作；不提供直接编辑已批准对象或正式 Prompt 的输入框。
- **事件/日志窗口**：任务阶段、解析/抽取/编译版本、耗时、警告、阻断原因、Gate 决定、access_audit ID 和交付状态。日志可筛选，但不可替代结构化状态。

#### 4.10.3 首版必须显示的参数与数据

| 区域 | 必显参数/数据 | 默认隐藏或脱敏 |
|---|---|---|
| 任务 | `task_id`、任务状态、创建人、更新时间、`session_id`、来源文件名/`source_id`/SHA-256、目标专家与确认方式 | 完整原始身份信息、无关参与人资料 |
| 证据 | `evidence_id`、`source/utterance/span` 定位、说话人/时间戳、`evidence_kind`、上下文 refs、原文哈希、派生处理版本 | D3 原文全文、候选人/JD 敏感字段 |
| 知识 | 对象 ID/类型/版本/状态、作用域、父版本、证据 refs、冲突集、是否进入当前组版本 | 未授权对象的完整原文和跨任务资料 |
| 变更 | `change_id`、类型、旧/新对象、基线、差异摘要、影响范围、所需 Gate、当前决定、阻断原因 | 非本任务的敏感证据 |
| 编译 | 组版本、政策版本、编译器版本、配置版本、LLM 模型/配置快照、Prompt 预算/实际大小、输入对象哈希、Prompt/manifest 哈希、编译结果 | API Key、内部服务凭据、模型密钥 |
| 交付 | 发布包 ID/版本、适用范围、交付方式、接收方、`integrity_verified/sent_unverified`、delivery ID、时间 | 原始访谈与候选人/JD 内容 |

任何 API Key、Token、Cookie、服务凭据和完整敏感原文不得以明文出现在普通参数面板、Prompt 预览、日志或发布包中。

#### 4.10.4 首版控制口

- **任务控制**：新建任务、导入 TXT、重复导入检测、重新解析（生成新解析结果，不覆盖原快照）、锁定/重新选择目标专家、暂停/恢复任务。
- **证据控制**：默认在后台完成 evidence_kind 候选分类、目标对象绑定和 G2 审计；遇到目标归属不清、冲突或证据不足时，在 Graph 详情中提示并允许退回补访/复核。不得因隐藏逐条证据页而放松服务端证据资格校验。
- **知识控制**：选择精确比较基线，在一张画布查看候选完整图/现有基线/增量差异，逐项查看结构与话术证据，并对整张候选 Graph 批准或驳回。整图批准在后台形成对应 G2/G3 审计并生成新的候选后继版本，不修改原基线。
- **编译控制**：选择已批准组版本与政策版本、生成编译草稿、查看 manifest/Prompt diff、重新编译、阻断发布、提交 G5；不提供手改正式 Prompt 的控制口。
- **发布/交付控制**：发布确认、导出发布包、复制 Prompt+核验卡、记录交付、重新计算/录入 Prompt SHA-256、标记 `integrity_verified` 或 `sent_unverified`。
- **审计/设置控制**：查看 access audit、调整非语义显示设置（主题、密度、日志展开级别、自动刷新）；角色、作用域、政策、评分权重、Prompt 规则等语义设置必须走受控变更，不得在“前端设置”里静默覆盖。

每个控制口都必须返回结构化结果（成功/待审核/阻断/失败）、状态变化、对象 ID/版本和审计 ID；不可只弹出“操作成功”而不说明实际版本或状态。

### 4.11 LLM 配置与辅助提炼模块（OPEN-P0-13，新增·MVP草案）

本产品在证据提炼、策略结构化、话术映射和评价 Prompt 生成环节借助大语言模型（LLM）的语义理解能力。LLM 不做自动决策；所有 LLM 产出均为候选提案，必须经过人工 Gate 审核才可进入已批准知识或发布包。

#### 4.11.1 LLM API 配置（MVP草案）

- 系统维护一份可配置的 LLM API 设置，存储于后端 `data/llm_config.json`，包含：`base_url`、`api_key`、`model`、`temperature`、`max_tokens` 和其他调用参数。
- API 采用 OpenAI `/v1/chat/completions` 兼容格式；`base_url`、`model` 和供应商均为运行时配置。当前本地验证快照使用公司 `https://token-hub.in.taou.com` 与 `gpt-5.6`，后续切换兼容模型时不改变调用代码或产品契约。
- API Key 属于 D3 敏感数据，不得出现在前端普通参数面板、Prompt 预览、日志或发布包中；前端设置页可查看 base_url 和 model，但 key 默认脱敏显示。
- 前端"审计与设置"页新增"LLM 配置"入口，允许产品/运营人员查看和修改 base_url、model 和调用参数；修改 API Key 需额外确认并记录审计事件。
- 语义设置（模型选择、温度等）的修改属于受控变更，记录审计事件，但 MVP 允许同一人修改，不要求独立审批人。

#### 4.11.2 LLM 辅助环节与人工边界（MVP草案）

| 环节 | LLM 做什么 | 人工做什么 | 产出状态 |
|---|---|---|---|
| 证据提炼 | 在后台阅读完整访谈，识别策略支持、专家原话和上下文，提议 evidence_kind 分类 | 在 Graph 变化详情中按需复核；冲突/归属不清时退回 G2 | 候选证据 |
| 策略结构提炼 | 同时读取精确完整基线与新访谈证据，提议节点、边、候选人状态/反应和触发条件的增量变化 | 在一张完整 Graph/diff 画布上审核批准或驳回 | 候选 Graph 变更集 |
| 话术映射 | 将目标专家原话全文映射到行为节点，保留说话人、时间位置和证据 ID | 在 Graph 节点详情核对话术归属和原话证据 | 候选节点话术 |
| 电话执行 Prompt 生成 | 基于已批准专家克隆 Graph，生成供电话模型使用的条件反应、动作、话术、停止条件和未知情境处理指令 | G5 核验克隆忠实度、Prompt 完整性和哈希 | 编译草稿→执行发布包 |
| 评价 Prompt 生成 | 基于与执行 Prompt 相同版本的已批准专家克隆 Graph，生成策略评价 Prompt 和话术评价 Prompt | G5 核验基线一致性、Prompt 完整性和哈希 | 编译草稿→评价发布包 |

#### 4.11.3 LLM 产出的硬约束

- LLM 提议的所有策略节点、边、话术和 Prompt 均为候选，status=`candidate`，不自动进入已批准知识或编译输入。
- LLM 必须标注其提议的证据回链（source/utterance/span）；无证据回链的提议标记为 `insufficient_evidence`，不进入 G3。
- LLM 不得补全缺失的边或虚构节点；未连接的局部结构记录为 Fragment，不得自动补边。
- 执行 Prompt 和评价 Prompt 生成时，LLM 只接收同一明确版本中的已批准对象（approved-only）；候选、冲突未决和未批准对象不进入 Prompt 生成输入。
- LLM 调用参数和模型版本记录在编译 manifest 的 `llm_config_snapshot` 中，确保可复现。
- LLM 调用失败或超时时，对应环节标记为 `llm_error`，不静默降级为规则拼接。
- 前端展示并允许修改的模型、温度、`max_tokens`、采样/上下文数量等参数必须与本次请求实际生效值一致；后端不得用未展示的硬编码值静默覆盖。每次分析运行记录最终有效参数，而不仅记录配置文件默认值。
- 正式整份访谈增量学习不得使用逐发言字符截断、逐节点话术截断或“只取前 N 条”作为静默省钱手段。受模型提供方硬上限约束时，系统应显式报错或采用可审计的分批/合并流程，不得将不完整输入伪装为完整提炼。
- 当前高质量调用档采用模型可接受范围内的高输出预算、长超时和思考模式；连接测试可使用极小的确定性请求，但连接测试参数不得冒充正式分析参数。当前实现基线为 `max_tokens=65536`、`timeout=900s`、`thinking.enabled=true`，变更后须同步更新设置页与运行快照。

#### 4.11.4 分析运行身份、复用与失效（v0.38 补充·硬约束）

每次证据分类、策略提炼和话术映射均生成不可变 `analysis_run`。其输入指纹至少包含：来源快照哈希、任务 ID、当前目标专家稳定标识/确认版本、所选基线 ID/版本/内容哈希、实际发送的证据与上下文引用、有效 `max_utts`/窗口参数、模型与调用参数、提示词模板版本和输出 Schema 版本。

只有上述输入完全相同且前次运行成功时才允许复用；任一输入变化必须生成新运行。复用响应必须显示被复用的 `run_id`、原运行时间、输入摘要和复用原因，不得让用户误以为模型刚刚重新执行。失败、部分写入、旧提示词、旧目标专家或旧基线的运行不得命中完成态缓存。

#### 4.11.5 精确基线增量学习与 Graph 审核契约（v0.41 补充·硬约束）

1. 正式提炼输入按固定顺序组成：先发送用户在 G1 选定的不可变 Graph 基线完整结构（节点、边、触发器、节点话术、`baseline_id/version/content_hash`），再发送本次完整访谈的结构化证据。不得只发送基线摘要、截断话术或靠名称猜测基线对象。
2. LLM 对每个节点、边、触发器输出 `candidate_key`、`change_type`、`baseline_refs`、`evidence_refs`、`script_evidence_refs` 和 `reason`。`change_type` 至少支持 `add/modify/deprecate/split/merge/keep`；凡非 `add` 变更必须引用准确基线稳定 ID，服务端必须拒绝不存在、跨基线或类型不匹配的引用。
3. `evidence_refs` 只能把目标专家本人亲口表达或结合上下文明确认可的内容作为策略支持；其他人的发言进入独立 `context_refs`。`script_evidence_refs` 只能引用目标专家原话，并在候选节点与批准后的话术片段中保存全文、说话人、时间戳和原始 utterance/evidence ID。
4. 候选存储可以保留“增量变更集”，但用户看到并审核的候选 Graph、进入 Prompt 编译的批准 Graph，都必须由服务端确定性物化为“未变化基线对象 + 有效变更对象”的完整图。编译不得只读取增量对象而丢失基线未变化部分。
5. Graph 审查提供三种同画布模式：候选完整图、现有基线、增量对比。增量对比用颜色和映射关系标识保留、修改、新增、拟废弃，不拼成左右两张互不连接的图。点击变化对象必须显示结构依据、目标专家原话证据和可回听时间位置；其他人上下文折叠显示并明确“不可归因”。
6. 人工批准/驳回以整张候选 Graph 为当前 MVP 操作单位。批准动作须在后台逐项执行目标专家资格、证据引用、基线引用与 Graph 完整性校验，写入 G2/G3 审计，并生成准确专家原话片段；任何 LLM 结果都不得自动批准、自动覆盖旧基线或自动发布。
7. 候选边/触发器的端点既可引用本次候选节点，也可引用同一精确基线中未变化的节点；服务端必须按基线 ID/版本/哈希验证后一并接受，不得因基线节点未被复制成候选知识对象而误拒绝。任何未通过服务端校验的模型变化必须在 Graph 页显式显示，并阻断整图批准。
8. 正式高质量调用可能持续数分钟。模型请求不得独占后端主服务并冻结健康检查、任务切换或其他只读页面；发起端提前断开时，已在执行的服务端任务仍应完成候选落库，用户可刷新查看最终候选，不得把客户端断线等同于模型失败。
9. 边的条件是 Graph 可执行与可评价的核心语义，界面不得用边 ID、空白或任意占位符冒充条件。若某节点只有一条有效出边且该边原始条件为空，可确定性标记为“无条件顺序衔接（完成上一步后继续）”，并明确注明原图未填写显式条件；若同一节点存在多条有效出边而任一出边条件为空，则属于无法判定走向的 `missing_branch_condition`，Graph 页必须显式告警并阻断整图批准及 Prompt 编译，直到通过有审计的基线新版本或候选变更补齐，不得由前端、服务端或 LLM 猜测专家条件。

#### 4.11.6 同源双 Prompt 产物的定义

本产品从同一个已批准专家克隆 Graph 版本编译两类用途不同的 Prompt。发布 manifest 必须记录共同的专家、策略话术组版本、知识对象集合和内容哈希，防止执行标准与评价标准漂移：

1. **电话执行 Prompt**：作为电话模型系统提示词的一部分，将已批准 Graph 编译为可执行的条件反应规则，包括候选人状态/反应、猎头动作节点、分支与优先级、停止条件、节点话术及缺少证据时的保守处理。其首要目标是忠实执行选定专家克隆版本，而不是由模型自行优化、融合或补全专家未表达的做法。
2. **评价 Prompt**：以同一已批准 Graph 为标准，评价 AI 猎头在电话中的行为轨迹和表达与该专家克隆基线的符合程度。评价至少拆为：
   - **策略流程评价 Prompt**：评价该走的节点是否执行、该触发的分支是否触发、该停止时是否停止，以及未知情境下是否越过证据边界。
   - **话术评价 Prompt**：以已批准的节点话术（专家示范原话、表达功能、句法、用词和语感）为标准，评价 AI 猎头在对应节点上说了什么、怎么说、和专家表达是否接近。

策略和话术评价可合并为一个综合评价 Prompt（策略 60% + 话术 40%），也可分开使用；编译配置在发布包 manifest 中记录采用方式。MVP 默认生成一份电话执行 Prompt、分开的两种评价 Prompt，并提供评价合并版。专家相似度、业务效果和公司合规性是不同评价维度：电话表现可能有效但不像该专家，也可能像该专家但触发公司 Guard；系统不得用效果或合规结果替代克隆符合度判断。

#### 4.11.7 节点原话选择与人工校准版本（v0.43 补充·硬约束）

1. Graph 右栏“目标专家原话”按节点提供话术选择与人工校准，但不得修改不可变访谈证据。每个原始证据始终保留说话人、时间位置、证据 ID 和初始 STT 文本；人工听录屏后的修正保存为独立 `script_fragment` 版本，并继续回链该原始证据。
2. 一个节点可选一条或多条原话；每个原始证据槽位同时只能采用初始版或一个人工保存版本。多条选中内容作为独立话术范例进入 Graph 物化和 Prompt，不得静默拼接成一段。旧候选没有显式选择字段时，兼容解释为全部 `script_evidence_refs` 的初始版已选。
3. 编辑器采用显式保存：未保存文本只存在前端；“重置”只把当前编辑框恢复到访谈初始版，不删除任何已保存版本，也不改变服务端已保存选择。保存版本不立即进入 Prompt，须先保存节点选择，并随整张候选 Graph 批准后才成为 approved-only 输入。
4. 未批准且未被编译/发布引用的人工保存版本可永久删除；若删除的是当前采用草稿，节点该槽位自动回退访谈初始版。原始访谈证据、已批准版本和历史编译/发布引用版本不得删除。已批准 Graph 只读，后续校准必须进入新的候选 Graph。
5. 整图批准只冻结当前选中的话术版本：初始版生成不可变 approved `script_fragment`，人工版由候选冻结为 approved；未选版本保持草稿且不得进入 Prompt。Graph 物化与话术 Prompt 必须读取同一选择，保留完整文本，不得使用固定字符数静默截断；只受发布包整体显式预算约束。
6. 当前继续复用 `db.json` 和 `script_fragment`，不为文本版本引入独立数据库或常驻缓存。若真实数据达到数万版本、文件约 50 MB 或出现可测加载退化，再评估 SQLite/按节点懒加载迁移，不提前扩张。

#### 4.11.8 边条件人工校准与无损路由语义（v0.44 补充·硬约束）

1. Graph 右栏允许人工直接校准一段规范“路由条件”，不得把边拆成必须逐项填写的正例、反例、优先级等繁重表单。端点、目标专家证据、回听位置、版本与审计由系统维护；原始模型/基线条件不可变，人工条件作为候选边当前规范文本保存。
2. 非空但模糊、概括性强或边界未穷尽的条件仍是合法知识，可以批准和编译。条件是供下游 LLM 结合完整对话进行语义判断的线索，不是关键词白名单；可选信息缺失表示“未知/未提供”，不得自动解释为否定、不适用、禁止或反向条件。
3. 单独人工确认仅强制用于问题边：多出口空条件、模型明确标记的不确定边、人工修改后未保存的边，以及同一来源使用完全相同条件却指向不同目标的边。其余清晰提炼条件随整图批准一并确认，不要求用户逐条点击。语义相近但文本不同的模糊条件不得由脆弱启发式自动判冲突。
4. 单出口空条件仍可确定性物化为“完成上一步后继续”；多出口完全空条件继续阻断批准和编译。同源、同规范条件、不同目标属于不可执行冲突，必须修改条件或结构后才能放行。信息有限但已有非空条件不得因未填附加字段而被废弃。
5. 编辑继承自不可变基线的边必须创建或更新引用精确基线边的候选 `strategy_edge modify`，不得回写基线内容。已批准 Graph 只读；每次候选条件确认记录原条件、确认条件、审核人和时间，后续修改进入新候选版本。
6. 物化 Graph、电话执行 Prompt 和策略评价 Prompt 必须共享同一确定性权威路由表。路由表逐字保留当前规范条件，并计算独立哈希；任何 LLM 生成环节不得用概括文本替换或删减权威路由表。专家原话继续作为证据回链，不默认整段进入运行 Prompt。
7. 电话执行 Prompt 必须包含完整节点、已选择节点话术、权威路由表、停止条件及 Graph/基线身份，并明确：结合上下文理解模糊条件；未提供不等于否定；多条路线都可能时可合理判断并在必要时自然澄清；不得发明 Graph 中不存在的路线。策略评价 Prompt 使用同一规则，证据不足时输出“无法判断”，不得只因未出现精确关键词判错。
8. 编译、发布和交付记录必须新增电话执行 Prompt 正文/哈希与权威路由表哈希，并与两种评价 Prompt 记录同一 Graph、基线和话术选择身份。旧 Graph 缺少校准字段时继续读取既有 `condition`；旧发布记录保持可读，不执行破坏性迁移。

#### 4.11.9 导入基线编辑与规范 Graph 复用（v0.45 补充·硬约束）

1. draw.io 或规范 Graph JSON 导入结果均作为不可变参考基线保存。人工在候选 Graph 中编辑继承节点或边时，不得回写该基线；节点文本编辑生成/更新精确引用原节点的 `strategy_node modify`，边条件继续生成/更新精确引用原边的 `strategy_edge modify`。
2. 候选节点与继承节点共用一个最小节点文本编辑器；候选边与继承边共用现有路由条件编辑器。节点/边端点、基线 ID、版本和内容哈希由系统维护，不要求用户手填。已批准 Graph 只读，后续编辑必须进入新候选。
3. 物化 `modify` 时只覆盖人工或模型明确修改的语义字段；基线节点的脚本、证据引用、上下文、位置、类型和元数据，以及基线边的端点、证据、上下文、条件审核信息和元数据，未被修改时必须保留，不得因为转成候选对象而静默丢失。
4. 系统须可将当前物化 Graph 导出为确定性 `ai-call-strategy-graph` JSON，并可在另一任务中重新导入为公共参考基线。导出文件保留节点、边、触发器、停止条件、已选择话术、证据/上下文引用、回听位置、条件审核信息、Graph/基线来源身份和内容哈希；导入后重新计算本地基线哈希。
5. 规范 JSON 导入与 draw.io 稀疏导入共用同一归一化器。旧手搓 Graph 缺失证据、上下文、话术、审核或元数据字段时，分别归一化为空数组、空字符串或空对象；缺失表示“未提供”，不得伪造证据、话术或否定语义，也不得因此拒绝整个基线。节点 ID、边端点和数组类型等结构完整性仍须严格校验。
6. 公共基线携带的证据引用仅作为可移植来源标识保存；若导入包未同时包含本地可验证的不可变证据正文，系统不得把这些引用冒充为当前任务已审核证据。后续访谈产生的新证据继续走当前任务的目标专家归属和 Gate 校验。

#### 4.11.10 电话流程分区布局与展示标注（v0.46 补充·已确认）

1. Graph 默认提供“电话流程布局”，按外呼前准备、接通与身份许可、可用性与初始分流、意愿识别与异议处理、需求澄清与机会匹配、转化动作、收口与后续七个阶段从上到下展示；保留拓扑分层、原始坐标和网格模式。
2. 每阶段横向区分抗拒/负向、中性/未知、接受/正向。该方向仅是展示标注，不是策略质量、评价结果或关键词路由规则；规范边条件仍是唯一权威路由语义，布局信息不得进入电话执行或评价 Prompt。
3. 布局标注与 Graph 知识对象分离保存，不改变不可变基线、候选/批准 Graph、编译输入或其内容哈希。已批准 Graph 仍可调整展示布局；所有人工调整须记录任务、Graph、编辑人和时间。
4. 节点记录展示阶段和可选横向区域覆盖，边记录 `resistant / neutral / receptive / unknown` 展示方向。没有节点覆盖时由入边方向计算区域；多入口冲突、信息缺失或模型未提供均居中/待分类，不得自动解释为负向。
5. 每个物化 Graph 内容版本最多自动执行一次布局 LLM 分析并缓存。模型只可对输入中的稳定节点/边 ID 分类；遗漏或非法项按未分类处理。调用失败不得阻断 Graph 审核、批准、编译或发布，前端退回现有拓扑分层并允许重试。
6. 人工阶段/方向覆盖在 Graph 内容变化后按仍存在的稳定 ID 继续复用；新增或未覆盖实体重新分析。精确拖动坐标只在当前页面有效，不作为知识或持久化布局资产。
7. 规范 Graph JSON 可携带独立布局画像与布局哈希；导入时布局缺失或无效只产生警告，不阻断策略 Graph 导入，也不得改变策略 Graph 内容哈希。
8. 左/中/右只定义区域顺序，不是三个固定坐标。各区域必须按该阶段的节点数量动态向横向扩宽，并为每个节点分配独立槽位；阶段背景和区域标题随整图宽度扩展。默认视野居中首个有节点的阶段，用户通过平移阅读宽图，“适配”仅用于整图鸟瞰。

### 4.4 与已批准知识基线的语义对比

变更比较不能只关注结构文本差异，还需支持“结构不变但证据状态变化”的提案：

- `evidence_support`：新增支持证据，结构不变但置信度或证据覆盖提高。
- `counter_evidence`：新增反例或失败案例，提示降低适用范围/置信度或增加条件。
- `contradiction`：与现有知识冲突，要求并存、澄清或裁决，不得静默覆盖。
- `explicit_rejection`：专家明确否定旧规则，提议废弃、替换或标记来源变化。
- `scope_change`：适用范围、阶段、专家策略话术组作用域或有效期变化，结构可能不变。

这些证据型变更与 `add/modify/replace/deprecate/override/reclassify/split/merge` 等结构型变更分开呈现。

#### 4.4.1 证据型变更的处理规则（OPEN-P0-10，已在本版本定义·MVP草案）

- `evidence_support`：只增加对既有主张的原始支持，且不改变节点、边、话术、Guard、作用域或评价结果时，作为追加证据记录保存；不生成新的 Prompt，不改变已发布版本。若因此达到某个需人工确认的证据覆盖门槛，进入 G2/G3 复核，但不能自动提高评价分数或把候选变成 approved。
- `counter_evidence`：只说明存在反例、失败案例或适用条件缺口时，先追加反例并降低可用范围/标记待确认；若要改变规则适用条件、评价结果或发布包内容，必须同时提出相应的 `modify`、`scope_change`、`replace` 或 `deprecate` 结构变更。
- `contradiction`：与既有知识互相支持不足或直接冲突时，建立/更新 `conflict_set`，保留双方证据和时间/作用域；在人工裁决前不得静默选边，也不得把任一方标成已解决的唯一真相。冲突影响发布对象时阻断新版本/发布；不影响当前发布范围的冲突也必须在版本记录中明确排除。
- `explicit_rejection`：专家明确否定旧说法时，只能生成“拟废弃/拟替换”提案；是否代表旧规则一直错误、仅代表该专家现在改做法，或只是针对某个 case 的例外，须由 G2/G3 根据时间、作用域和上下文裁决。没有裁决不能自动 `deprecate`。
- `scope_change`：证据明确改变适用阶段、候选条件、专家策略话术组、有效期或例外范围时，必须记录旧/新作用域、`valid_from`/`valid_to`（如适用）和生效依据；只要影响 Prompt 适用性，就必须生成新知识/组版本并按 P0-05 回归和发布。

每条证据型变更至少记录：`evidence_change_type`、目标对象稳定 ID/版本、`evidence_refs`、来源 session、支持/反例/冲突关系、声明的影响（仅证据、待确认或影响语义）、作用域/时间、提出人和审核状态。原始证据追加不等于批准，模型置信度变化也不能替代人工决定。

证据型变更的最小审批为：G2 确认证据归类、目标和作用范围；若不改变可编译语义，可作为证据记录归档；若改变结构、适用性、评价结果或 Guard，必须转成相应结构/政策变更并经过 G3，涉及规范性政策时再经过 G4。只有语义变化进入新版本时才触发 P0-05 的回归；纯证据追加不触发回归，但必须保留可查询审计链。

已发布知识和发布包的证据链不可原地回写。证据追加使用新的 `evidence_update_id`/证据版本与父对象关联；旧 Prompt、旧包哈希和旧审核记录保持不变。需要让下游看到新的证据关联时，重新编译并生成新发布包版本，但不得把“同一 Prompt、仅证据增补”伪装成旧包已更新。

### 4.5 变更提案与人工审核

- `CHG-001`【已确认】新访谈提炼出的内容首先进入候选知识或变更提案状态，不得直接改写已批准的知识基线、策略话术组版本或已发布评价规则包。
- `CHG-002`【已确认】人工审核批准变更提案后，系统才可据此生成新的知识基线/策略话术组版本，并在其基础上编译新的双 Prompt 发布包。
- `CHG-003`【已确认】候选、待确认、已拒绝或仅存档的知识不得进入正式评价 Prompt；它们可以保留并继续作为后续补访、复核和变更比较的依据。
- `CHG-004`【已确认】变更提案、进入新知识版本和进入发布包是三个递进状态；一次明确原话可以支持生成候选提案，但任何变更都不得自动批准、自动生成新版本或自动发布。具体 MVP 门槛见 4.5.1–4.5.5。

#### 4.5.1 提案的统一最小信息与生成门槛（MVP草案）

所有 `add`、`modify`、`replace`、`deprecate`、`override`、`reclassify`、`split`、`merge`、`link`、`attach`、`unlink`、`detach` 和 `overlay` 提案至少记录：`change_type`、受影响对象/基线的稳定 ID 与版本、候选内容或关系、原始 `evidence_refs`、适用范围、提出原因、差异摘要和当前状态。

- 一条语义明确、可定位且未被已知证据直接冲突的专家原话，足以生成候选提案；它不等于已批准知识，更不等于可发布内容。
- 仅由模型常识、推断或不完整上下文得出的内容可以保存为候选，但必须标记证据缺口/不确定性；未补足前不得在 G3 获批。
- 每一项新增或改动后的可编译主张都必须直接回链至少一处原始证据。涉及关系的提案还必须标出所有端点的稳定 ID；无明确端点或基线时不得伪装成关系变更或 Overlay。
- `support`、`counterexample`、`contradiction`、`explicit_rejection` 和 `scope_change` 等证据型变化独立展示，不得借由附加证据静默改变已批准对象；其专门版本规则仍由 `OPEN-P0-10` 定义。

#### 4.5.2 按变更类型的 MVP 证据与差异门槛（MVP草案）

| 变更类别 | 包含类型 | 进入 G3 前的最低要求 |
|---|---|---|
| 局部内容/归类/连接 | `add`、`modify`、`reclassify`、`link`、`attach` | 每项候选内容或关系有原始证据回链；`modify/reclassify` 展示旧值与新值；`link/attach` 明确源端、目标端及连接依据。 |
| 结构或有效性变化 | `replace`、`deprecate`、`split`、`merge`、`unlink`、`detach` | 满足上一行要求，并列出受影响的已批准对象/版本、旧结构与新结构差异，以及为何替换、废弃、拆分、合并或断开。若证据只表明存在新内容而未表明旧内容失效，只能提出 `add` 或候选并存，不得直接 `replace/deprecate/unlink/detach`。 |
| 条件性覆盖 | `override`、`overlay` | 满足结构变化要求，并必须引用同一专家策略话术组内的已批准基线，明确触发条件/适用范围、被覆盖或叠加的位置和未触发时不改变的基线。缺少基线或条件时改按普通结构变更/Fragment 提案处理。 |

`merge` 同时是一个结构变更类型；当其表示 Fragment 挂接或合并时，仍须分别说明各对象的来源、关系依据和合并后差异，不能因为名称相同而自动合并。

#### 4.5.3 审批与新知识版本门槛（MVP草案）

- 所有结构或语义变更均必须经过 G3 知识审核；MVP 不存在按类型自动接受的变更。
- 涉及公司级 Guard、禁用规则、评分底线、敏感数据处理或强制动作时，在 G3 外还必须通过 G4；无政策责任人或未获得显式决定时阻断。
- 变更可生成新的知识基线/策略话术组版本，当且仅当：已通过所需 Gate；候选对象均为 `approved`；原始证据回链率为 100%；引用的父版本、基线、端点和适用范围可解析；未决冲突已被显式裁决或未进入该版本；以及差异摘要与审核记录完整。
- G3 可作出批准、驳回、仅存档或请求补充/修改四种决定。请求补充/修改不生成版本；驳回与仅存档不进入 Prompt。

#### 4.5.4 回归触发与 MVP 最小验证（MVP草案）

只要已批准变更预计会改变已发布组的编译结果、评价行为、适用范围或 Guard，就必须在发布前触发回归。上述所有结构/语义类型在被纳入发布包时默认属于此类；仅不改变已批准语义的证据附件不在本节自动触发范围。

MVP 的最小回归不是自动化门槛，而是：审核者核对可读的 Prompt/规则差异；若存在适用的历史 case，至少人工复跑一个受影响 case 并保存结果。若尚无适用 case，可继续发布，但必须在发布记录中标记 `regression_gap`、说明原因和预期风险，并由 G5 显式接受该缺口。不得将“没有 case”记录成“已通过回归”。

#### 4.5.5 进入发布包的门槛（MVP草案）

变更只有在新策略话术组版本已经生成、所需 G3/G4 审核完备、最小回归或已接受的 `regression_gap` 已记录、编译所得 Prompt 与发布包哈希已固定且 G5 发布确认完成后，才允许进入发布包。G5 只确认待发布包与已批准版本、哈希和记录的一致性；如发现内容问题，必须退回新的变更提案，不能在 G5 原地编辑。

### 4.6 知识版本发布与独立策略作用域

- `SYS-001`【已确认】每位 Top 猎头的策略体系独立建模和版本化；不得默认将专家 A 与专家 B 的知识直接拼接。
- `SYS-002`【已确认】若未来开启跨专家吸收，必须先判断两套策略是否结构兼容、目标一致、前提一致和组合后仍保持内部一致性；该能力不进入 MVP。
- `SYS-003`【已确认】两位专家可能分别形成自洽、有效的局部最优策略体系，跨体系强行融合可能降低效果。因此，专家策略话术组必须允许并行存在；MVP 不以融合为前提，也不得自动把多个专家合成为统一标准。
- `SYS-004`【已确认】MVP 只允许从已批准的专家策略话术组中整套选择；组内 Graph、Fragment 和 Overlay 是否纳入由知识更新、审核和版本发布决定，评价运行时不提供零件级选择。MVP 不提供跨专家 fragment/overlay 拼装，也不承担跨体系兼容性或局部最优融合判断。
- `SYS-005`【已确认】专家策略/话术默认是描述性知识，只进入其所属或经批准包含它的策略话术组；规范性政策/Guard 是单独版本化的“应当如何评价/哪些行为禁止”规则，只有在明确批准的作用域内才能跨组共用。专家的一句“我会/我不会”或模型推断都不能自动升级为公司级规则。
- `SYS-006`【已确认】每个双 Prompt 发布包版本只引用一个已批准、可版本追溯的专家策略话术组版本，但不与某个具体公司 AI 猎头永久绑定。同一策略话术组版本可因规范性政策或编译版本不同生成多个发布包版本。电话运行方与评价方必须明确选择并记录本次采用的同一发布包版本；本产品不根据电话内容自动猜测或切换专家标准。
- `SYS-007`【已确认】如果未来允许跨专家融合，融合结果必须先形成一套独立命名、独立审核、独立版本化并经过历史 case 回归验证的组合策略话术组，再作为新的可选评价标准出现；不得在评价运行时临时拼接。
- `SYS-008`【已确认】同一专家默认维护一套策略话术组；当人工明确认定该专家存在目标、前提或运行逻辑不同且各自自洽的多套打法时，允许拆为多个可独立选择、独立审核和独立版本化的策略话术组。
- `SYS-009`【已确认】系统可根据新访谈提出“更新既有组”或“新建策略话术组”的变更提案，但不得仅因出现多个未连接 Fragment 就静默拆组；有证据的同专家 Fragment 连接/合并应优先作为既有组更新提案。新建或拆组必须经过人工确认。
- `SYS-010`【已确认】当同一专家已有已批准基线时，后续访谈或新增材料可以相对该基线提出 Overlay 候选；该候选仍须经过证据审阅和版本审核，不能因为属于二次访谈/二次触达就自动进入已发布组。它与同一专家 Fragment 到 Graph 的 `link/attach/merge` 不是同一种变更。

#### 4.6.1 描述性知识与规范性政策边界（OPEN-P0-09，已在本版本定义·MVP草案）

- **描述性知识**记录某位专家实际采用或明确说明的策略、节点、条件、话术和经验规律。它回答“这位专家在什么条件下怎么做/怎么说”，默认只对相应策略话术组生效；即使表达中出现“必须”“永远”等强词，也不因此成为公司政策。
- **规范性政策**记录评价时必须遵守的公司/团队/产品规则，例如禁用行为、敏感数据处理、评分底线、强制动作和统一输出要求。它回答“在本作用域内评价必须如何判定”，独立于某一位专家的个人打法。
- 无法判断属于哪一类、只有访谈中的推断或单一专家建议时，先作为描述性候选或待确认项保存；不得因为模型认为“更合理”而跨组生效。

规范性政策对象必须单独拥有稳定 ID、版本、责任人、作用域、来源依据、适用/失效时间（如有）、冲突说明和 G3/G4 审批记录。政策来源可以是公司政策文件、风险/法务决定或人工明确授权；专家访谈原话只能作为背景或提议依据，不能替代政策责任人的批准。

MVP 采用三类作用域：`group`（仅一个策略话术组）、`team/product`（指定团队或产品范围）和 `company`（公司级）。`group` 作用域的规范性规则仍不等于描述性知识，但不跨组生效；只有 `team/product` 或 `company` 作用域的已批准政策，才可在其声明的多个策略组发布包中复用。未声明作用域的政策不得编译。

#### 4.6.2 从专家知识升级为共享政策的最小门槛（MVP草案）

系统可以基于一条或多条专家证据提出“政策候选”，但不得自动升级。进入共享政策版本前，至少需要：明确的规范性措辞或人工政策主张、政策适用作用域、受影响评价对象/组、政策来源与原始证据引用、风险与例外说明、与现有政策的冲突检查、G3 知识审核以及 G4 政策责任人显式批准。无法提供责任人或作用域的候选只能留在原专家组/待确认状态。

政策与描述性知识冲突时，已批准且适用的硬性政策/Guard 优先；普通政策冲突或作用域重叠而未裁决时阻断发布，不由编译器按文本顺序或“最新内容”静默选择。策略组可以更严格地描述自己的做法，但不得通过专家知识放宽适用的公司级禁用规则或评分底线。

发布包的 `策略编译配置` 必须分别列出描述性知识来源和所引用的规范性政策版本。描述性知识只在组版本范围内编译；政策只在其批准作用域匹配时编译。任何未版本化的共享 Guard、默认评分规则或“大家都这么做”的隐含约定都不得进入 Prompt。

### 4.7 电话执行与评价双 Prompt 编译

- `OUT-001`【已确认】从同一已批准专家克隆 Graph 及适用的规范性政策，借助 LLM 分别编译电话执行 Prompt、策略流程评价 Prompt 和话术评价 Prompt（见 4.11.6）；编译器记录 LLM 配置快照、共同知识输入及每份 Prompt 的用途和哈希，确保可复现且执行/评价标准不漂移。
- `OUT-002`【已确认】MVP 的正式交付物为“专家克隆双 Prompt 发布包”，不只是一段裸 Prompt；包内必须明确区分供电话模型使用的执行产物和供评价 Agent 使用的评价产物。
- `OUT-003`【已确认】发布包至少包含：各用途可复制使用的 Prompt、发布包版本、专家策略话术组 ID/名称/版本、知识基线版本、变更摘要、用于人工/文件交付的执行输入契约、评价输入/输出契约和回归验证结果；这些契约是发布包的自描述内容，不等于系统间 API 集成协议。
- `OUT-004`【已确认】发布包将知识来源、编译配置和适用范围拆为三个独立字段：
  - `专家来源`：记录知识证据由哪些 Top 猎头提供，只用于追溯，不表示将多位猎头合并为统一人格。
  - `策略编译配置`：记录该发布包对应的专家策略话术组 ID、名称和版本，以及组内纳入编译的已批准 Graph/Fragment、已批准 Overlay、节点话术、Guard 和评价政策版本；如包含 Overlay，另记录其基线引用、触发/适用范围、作用位置、变更操作和版本。未批准或不具备编译资格的候选对象（包括 Overlay 候选）不得进入 Prompt。
  - `评估适用范围`：只记录电话触达阶段，可选“首次触达”“二次触达”或同时覆盖两者。
- `OUT-005`【已确认】发布包在本产品内生成、下载并保留交付记录；MVP 由产品/运营人员人工复制或导出后分别交给电话模型使用方和外部评价平台，不由本产品调用其接口。
- `OUT-006`【已确认】发布包必须具有可唯一选择的名称、ID 和版本。MVP 不建立“公司 AI 猎头—发布包”的长期绑定关系；发布包自身携带版本信息，交付说明应要求电话运行和评价任务记录本次采用的发布包 ID 与版本，本产品不负责写入外部任务。
- `OUT-007`【已确认】Prompt 是不可手改的编译产物；任何会改变执行行为、评价规则、权重、Guard 或适用范围的人工修改，必须回到结构化源对象或编译配置，形成新的版本并重新走审核、回归和发布确认。

#### 4.7.1 编译输入与可复现性（OPEN-P0-07，已在本版本定义·MVP草案）

一次编译只能接收一个已批准的专家策略话术组版本及其明确纳入的已批准对象：Graph、Fragment、Overlay、节点/边/触发器、绑定话术、Guard，以及已批准的评价政策/编译配置。候选、待确认、被拒绝、仅存档、已废弃或不在该组版本内的对象一律不得进入输入。

编译器不得猜测对象归属、补全缺失关系、跨组拼接，或把多个专家来源合成为一套标准。Overlay 只按组版本中已批准的基线、条件和变更内容编译为显式规则；MVP 不在评价运行时动态选择、嵌套或合成 Overlay。

编译、发布、交付和对应列表查询必须显式绑定并校验 `task_id + strategy_script_group_id + version`。服务端不得因调用方漏传 `source_id`、任务不存在或前端仍持有上一个任务的选中项而退化为“读取全部已批准对象/全局最后一条产物”；任务或组不匹配时必须阻断。切换任务后，前端须清空并按新任务重新加载编译、发布和 Gate 选择状态。

每次编译必须生成不可变 `compile_manifest`，至少含：编译器版本、目标策略话术组 ID/版本、全部输入对象及其版本/哈希、评价政策与编译配置版本、适用范围、各 Prompt 的用途与大小预算、编译时间、各输出 Prompt 哈希和发布包草稿 ID。相同输入与相同编译器版本应产生相同输出；否则阻断发布并记录差异。

#### 4.7.2 编译后的规则优先级与评价结果（MVP草案）

编译出的执行与评价 Prompt 必须共享以下规则优先顺序；其中结果状态和评分字段仅适用于评价 Prompt：

1. 发布包的评估适用范围与前置条件；范围不匹配时输出 `not_applicable`，不作评价或扣分。
2. 当前发布包显式纳入且适用的已批准 Guard/评价政策；其中被标为硬性限制的规则优先于策略与话术。
3. 已批准策略结构：节点、触发器、边、条件和已经在组版本中确定的 Overlay 结果。
4. 与节点绑定的已批准话术：用于判断该节点的表达质量和实现方式，不能反向改写策略结构。
5. 已批准评价政策定义的维度、权重、汇总与输出格式。

公司级政策与组内描述性知识的归属已由 `OPEN-P0-09` 的 4.6.1–4.6.2 定义；编译器只服从发布包显式引用且作用域匹配的已批准政策，不能隐含注入未版本化的“默认公司规则”。

若适用范围匹配但录音/转写无法充分支撑判断，输出 `insufficient_evidence`；不得因信息缺失直接判为失败。`fail` 只可由与已发布规则相矛盾的可观察证据触发，或由已批准政策明确规定的、在证据覆盖足够时可判定的必需行为缺失触发。输出必须同时给出命中的规则/节点稳定 ID、结果状态、所依据的通话证据和简短理由。

数值权重、聚合分数、阈值和 NA 细则只能来自已批准的评价政策版本，不得由编译器或下游模型自行补全；若未提供可用的数值政策，MVP 只允许编译为定性逐项评价，不输出虚构总分。

#### 4.7.3 去重、超长与人工修改边界（MVP草案）

编译器按稳定 ID 去重对象；同一节点的多条话术变体必须保留各自 ID、适用条件和来源，不得因文本相近自动合并或随机择一。组版本决定纳入哪些 Graph、Fragment 和 Overlay，编译器只序列化已批准决定，不作语义删改。

每个编译配置必须声明 `prompt_size_budget`。超过预算时，编译失败并阻断发布；系统可以报告超长来源，但不得静默截断、压缩、删去规则或改写话术来“凑长度”。需要压缩时，必须产生可审核的源知识/编译配置变更和新版本。

人工可在发布包外添加交付说明，但不得直接编辑已哈希的 Prompt。任何人工编辑后的文本都不再是正式 Prompt；若需要采用，必须回写为受控变更并重新编译，形成新的 Prompt 哈希和发布包版本。

#### 4.7.4 发布包自描述与人工交付（OPEN-P0-08，已在本版本定义·MVP草案）

MVP 的发布包是一个不可变的逻辑交付单元，可作为文件夹、压缩文件或系统导出物交付；具体封装格式不改变其中内容和校验规则。每个发布包至少包含以下内容：

| 内容 | 最小要求 |
|---|---|
| `release_manifest` | 发布包 ID、名称、版本、状态、生成时间、发布责任人、父/替代发布包（如有）、策略话术组与知识版本、编译器/评价政策/配置版本、适用范围、各 Prompt 用途与 SHA-256、按规范化 manifest 内容计算且排除自身字段的 manifest SHA-256、回归状态及 `regression_gap`（如有）。 |
| 正式 Prompt | 完整、可复制且明确标记用途的电话执行 Prompt、策略评价 Prompt、话术评价 Prompt 及评价合并版；每份正文必须与 manifest 中对应哈希一致。 |
| 执行输入契约 | 电话模型运行时可获得的候选人发言、对话历史、触达阶段和必要上下文；缺少 Graph 支持的情境时使用已批准的保守处理，不得自行虚构专家策略。 |
| 评价输入契约 | 下游评价时所需的电话转写/可用通话内容、能区分评价对象与候选人的角色信息、触达阶段及必要上下文；缺失时应按 Prompt 输出 `not_applicable` 或 `insufficient_evidence`，不得自行补猜。 |
| 评价输出契约 | 每项评价的规则/节点 ID、结果状态、通话证据引用、理由；仅在发布包显式纳入数值政策时输出相应分项/总分。 |
| 变更与验证摘要 | 相对父发布包的变更摘要、受影响范围、G3/G4/G5 审核记录引用、最小回归结果或被接受的 `regression_gap`。 |
| 交付核验卡 | 发布包 ID/版本、Prompt SHA-256、适用范围、交付日期、人工核验步骤与“不得手改 Prompt”的说明。 |

发布包默认不包含原始 Top 猎头访谈、原始评价通话、候选人/JD 原文或完整证据文本；它们只以受控的对象/证据引用存在于平台内。需要导出此类原文的权限和审计规则仍由 `OPEN-P0-11` 定义。

#### 4.7.5 人工交付与核验流程（MVP草案）

G5 发布后，产品/运营人员可选择“导出发布包”或“人工复制 Prompt”两种 MVP 交付方式。两种方式都必须同时提供交付核验卡；交付说明、Prompt 和 manifest 不得被拆成无法相互核对的无版本文本。

1. 交付人选择一个已发布包版本，核对 ID、版本、适用范围、Prompt SHA-256 与 G5 状态。
2. 导出时，导出物必须包含完整发布包及核验卡；人工复制时，交付人必须同时传递正式 Prompt 和核验卡，且不得在复制后修改正文。
3. 交付人或接收方以收到的 Prompt 重新计算 SHA-256，并与核验卡比对；一致才记录为 `integrity_verified`。MVP 不要求接收方登录本平台或提供平台 API 回执。
4. 平台保存 `delivery_record`：交付尝试 ID、发布包 ID/版本、Prompt 哈希、交付方式、交付人与接收方标识、时间、核验状态、核验人和备注。接收方未反馈时记录为 `sent_unverified`，不得伪称已核验或已被下游采用。

外部使用方若改写 Prompt、丢失核验卡或使用哈希不匹配的内容，该副本视为外部非受控派生物，不能以本产品的发布包身份登记或宣称通过 G5。纠正方式是重新交付原包，或创建新的受控版本；MVP 不建设外部系统的自动撤回、同步或回执能力。

### 4.8 历史 case 回归验证与发布门禁

待讨论。已确认：回归验证发生在候选变更获批、生成新版本之后，并在新双 Prompt 发布包交付前作为独立门禁；至少分别检查电话执行行为是否忠实于克隆 Graph，以及评价 Prompt 是否按同版 Graph 正确判定。具体 case 集合、指标、阈值和执行方式待定义。回归可以由本平台内置能力执行，也可以由人工在外部运行后上传结果，但不得把 EVALLAB 接入作为前置条件。

## 5. 数据源与数据模型

### 5.1 MVP 主数据源

- `SRC-001`【已确认】一次 Top 猎头访谈或讨论的交流记录文本，是一次知识更新任务的唯一必填输入数据源。
- `SRC-002`【已确认】首版接受飞书会议导出的标准 `.txt`。已核对的标准样本结构如下：
  1. 首行：会议日期、开始时间与会议总时长。
  2. `关键词:` 区域。
  3. `文字记录:` 标记。
  4. 重复发言块：`说话人标签 + 时间戳`，下一段为发言正文。
- 关键词区允许为空或不参与策略证据判定；最终证据以带说话人和时间戳的文字记录为准。

### 5.2 从主数据源派生的上下文

系统先从交流记录中识别会议元数据、参与人及角色、猎头身份、候选人信息、岗位信息和讨论上下文，再进入证据与策略抽取。派生字段不得脱离原文来源独立存在。

### 5.3 补录机制

交流记录中缺少必要字段，或系统无法唯一确定字段值时，才进入人工补录/消歧。哪些字段属于阻断任务继续的“必要字段”，将在人工确认点专题中确定。

### 5.4 核心知识层级

```text
专家（证据来源）
└─ 专家策略话术组（默认一套，经人工确认可有多套）
   ├─ 策略知识（当前连接状态）
   │  ├─ 已连接 Graph
   │  ├─ 尚未充分连接的 Fragment（可随补访挂接/合并）
   │  ├─ 猎头行为节点
   │  ├─ 候选人反应/状态与条件边
   │  ├─ 触发器
   │  └─ Guard
   ├─ Overlay（引用明确基线的条件性叠加对象；候选/已批准状态分开）
   └─ 节点话术
      ├─ 段落功能及顺序
      ├─ 句法结构及句式
      └─ 用词与语感
```

策略与话术分别版本化和比较，但通过稳定节点 ID 建立关联。

同一专家与策略话术组是一对多关系，但 MVP 采用“默认一组、人工确认后才拆组”的保守规则。一次访谈形成的知识可提出更新现有组、新建组、连接 Fragment 或创建 Overlay 的变更提案；在提案获批前，不得改变已发布组的边界。Graph、Fragment、Overlay 是否进入某个发布版本由审核结果决定，不由评价使用者临时选择。

### 5.5 MVP 最小知识 schema（OPEN-P0-02，已在本版本定义·MVP草案）

本节只定义对象边界、稳定身份、生命周期、版本关系、作用域和最小关联方式；不定义跨专家融合、运行时 Overlay 解释器或 Prompt 的具体编译模板。

#### 5.5.1 对象边界与稳定 ID

所有知识对象创建时生成一次稳定 ID。ID 只表达对象身份，不编码可变名称；名称、描述和展示标签可以修改，ID 不得复用。MVP 采用“类型前缀 + UUID”形式；原始证据采用可幂等定位的 `source_id + span` 组合，并保留来源文件哈希。

| 对象 | 稳定 ID 前缀 | 定义 | 直接归属 |
|---|---|---|---|
| `expert` | `exp_` | Top 猎头这一知识来源主体 | 全局 |
| `strategy_script_group` | `grp_` | 同一专家的一套独立策略/话术体系 | `expert` |
| `strategy` | `str_` | 策略层的行为结构、条件和判断 | `strategy_script_group` |
| `graph` | `gph_` | 当前已被证据连接的策略子图 | `strategy` |
| `fragment` | `frg_` | 当前尚未充分连接的局部策略知识 | `strategy` |
| `overlay` | `ovl_` | 相对于同组已批准基线的条件性叠加候选 | `strategy_script_group`，必须有 `base_ref` |
| `node` | `nod_` | 可观察的猎头行为节点 | `graph` 或 `fragment` |
| `edge` | `edg_` | 节点间带条件的连接 | `graph` 或 `fragment` |
| `trigger` | `trg_` | 触发节点/边/Overlay 的条件 | 所属策略对象 |
| `candidate_state` | `cst_` | 候选人反应、状态或条件 | 所属策略对象 |
| `script` | `spt_` | 节点下的段落功能、句法、句式和用词 | `node` |
| `guard` | `grd_` | 对策略执行或评价的限制条件 | `strategy_script_group` 或 `policy` |
| `policy` | `pol_` | 评价规则或公司级规范的承载对象 | 默认组内；公司级须明确批准 |
| `evidence` | `evd_` | 可回链到原始 TXT 的最小证据引用 | 来源文件/访谈 |
| `linkage` | `lnk_` | 两个知识对象之间的显式连接、挂接或合并关系 | 关联双方 |

`task`、`session`、`change_proposal`、`release_package` 属于任务与发布层对象，在 P1/P0 后续章节定义，不作为本节知识对象的隐式替代。

#### 5.5.2 状态规则

知识对象共享以下最小审核状态：`候选`、`待确认`、`已批准`、`已拒绝`、`仅存档`、`已废弃`。状态转换必须产生审计记录；`候选`、`待确认`、`已拒绝`、`仅存档`和`已废弃`对象不得进入正式评价 Prompt。

```text
候选 → 待确认 → 已批准
  ├──────────→ 已拒绝
  └──────────→ 仅存档
已批准 ──────→ 已废弃（仅由新版本或明确失效决定）
```

`Graph`、`Fragment`、`Overlay` 的形态不自动决定审核状态；是否进入某个已发布组版本只由证据审核、变更审核和版本发布结果决定。

#### 5.5.3 版本规则

- 已批准对象、策略话术组和发布包均不可原地修改；变更产生新版本，并保留 `parent_version_id`、`supersedes`、变更原因、证据引用和审核记录。
- 只补充证据、反例或作用域信息时，可以生成证据型变更记录；若改变结构、节点身份、边关系、话术绑定或 Guard，则必须生成新的知识版本。
- `node` 的稳定 ID在措辞或属性变化时保持不变；拆分、合并或语义身份改变时生成新 ID，并通过 `linkage` 和 `supersedes` 追溯旧对象。
- `overlay` 必须引用同一 `strategy_script_group` 内的已批准 `base_ref`；没有明确基线时不得创建 Overlay，应按 Fragment 或普通结构变更处理。
- 任务在 G1/变更提案中选定的基线必须以明确 `baseline_id + version/content_hash` 贯穿提炼、diff、话术映射、审核和编译；后端不得以数据库列表第一项、名称相同项或最近一项代替用户选定基线。
- `reference/immutable` 基线及其 Graph、节点、边和哈希不可原地增加话术、更新时间或其他业务字段。导入话术文档只能生成带来源和证据的候选话术/映射或新的候选知识版本；批准后再生成新版本，不能回写旧基线。任何内容哈希与当前规范化内容不一致时立即阻断 diff、编译和发布。
- 新访谈相对已选基线产生的候选对象必须保存 `change_type`、准确 `baseline_refs`、基线 ID/版本/内容哈希和差异原因。审核/编译使用的完整候选 Graph 由精确基线与候选变更确定性物化；未被变更命中的基线对象必须原样保留，拟废弃对象须显式标记而非静默消失。

#### 5.5.4 作用域与关系

作用域分成两个相互独立的轴：

1. `ownership_scope`：对象归属谁。MVP 允许 `expert`、`strategy_script_group` 和经明确批准的 `company_policy`；不得因内容相似自动跨专家升级。
2. `applicability_scope`：对象在哪里适用。采用 `可复用规则`、`条件适用`、`单一 case 观察`、`范围待确认`，并可另标记首次电话、二次电话或两者。

最小关系如下：

```text
expert
└─ strategy_script_group
   ├─ strategy
   │  ├─ graph / fragment
   │  │  ├─ node
   │  │  ├─ edge → trigger / candidate_state
   │  │  └─ script
   │  └─ overlay → base_ref（同组已批准版本）
   ├─ guard / policy
   └─ linkage（显式连接关系）

任一候选或已批准对象 ── evidence_refs ──→ evidence ──→ 原始 TXT span
```

MVP 不允许评价运行时对 Graph、Fragment、Overlay、node 或 script 做零件级临时拼装；编译输入必须是一个已批准的策略话术组版本。

#### 5.5.5 最小验收标准

- 同一对象改名、补充描述或新增证据后，稳定 ID 不变；导入重试不产生重复对象。
- 每个可进入审核的知识对象都能回链到至少一条目标专家原始证据，且能定位到来源文件、发言块和时间戳。
- 每个已批准版本都能追溯父版本、变更原因、证据、审核人和生成时间。
- 无明确基线的叠加内容不会被标记为 Overlay；跨专家内容不会在 MVP 中自动进入同一策略话术组。
- 任一候选、待确认、被拒绝或仅存档对象都无法进入 Prompt 编译输入。
- 对同一“基线 + 新访谈”运行，候选完整图可复现；修改对象能解析到准确基线稳定 ID，新增对象不伪造基线引用，节点话术能回链目标专家原话全文与时间位置。

### 5.6 证据与信息磨损（OPEN-P0-03，已在本版本定义·MVP草案）

本节定义“原始内容如何不丢、抽象内容如何回链、跨次访谈如何追加”的最小契约；证据语境能否升级为可复用规则，放到 `OPEN-P1-02` 单独讨论。

#### 5.6.1 原始来源不可变保存

- 每次导入先保存原始 TXT 字节快照，不在解析、清洗或导出时覆盖。来源记录至少包含 `source_id`、`sha256`、`byte_length`、`encoding`、`captured_at`、`imported_at` 和原始文件名。
- `source_id + sha256` 是一次来源快照的幂等键；同一快照普通重复导入不得生成新的知识版本，也不得覆盖已有来源。显式“任务重跑”不是新知识来源，而是对同一不可变内容发起新的独立处理运行；兼容实现可建立带 `origin_source_id` 的新 task/source 实例，但其内容哈希必须一致，且不得继承旧运行的审核和派生状态。
- 解析器可以生成结构化副本，但原始字节、原始发言顺序、原始时间戳和原始说话人标签必须保留。

#### 5.6.2 证据最小粒度与定位

证据采用三层定位，不把整份访谈复制到每个知识对象中：

1. `source_document`：原始 TXT 快照；
2. `utterance`：一个说话人 + 时间戳对应的完整发言块；
3. `span`：发言块中的半开区间 `[start, end)`，作为支持某个判断的最小引用片段。

每条 `evidence` 至少记录：`source_id`、`utterance_id`、`byte_start`、`byte_end`、展示用 `char_start/char_end`、说话人标签、起止时间戳、原文片段哈希和 `evidence_kind`。规范定位以字节偏移为准，字符偏移只用于界面展示。

#### 5.6.3 上下文窗口与抽象回链

- 上下文窗口通过 `context_refs` 引用相邻 `utterance_id`，不把上下文重新保存为一条新的证据。
- 解析、归纳、策略抽取、话术抽取和人工修改均必须记录 `source_evidence_refs`、处理类型、处理版本和处理时间。
- 任何 `strategy`、`node`、`edge`、`script` 或 `overlay` 版本，若要进入审核，必须能够沿 `evidence_refs` 回到原始 TXT 的具体发言块和 span。规范性 `guard`/`policy` 若来源是公司政策、风险/法务决定等非访谈材料，则必须回链到按同一不可变快照契约保存的受控 `policy_source_document`；若访谈只是背景依据则同时保留访谈引用。无法回链到相应不可变来源的内容只能作为推断、缺口或待确认项保存。
- 规范化文本、去除口头语、摘要、翻译或 AI 改写不得替代原文；如需保存，必须作为派生字段并保留原文引用和转换版本。

#### 5.6.4 跨次访谈与冲突保留

- 每次访谈拥有独立 `session_id` 和来源快照；同一专家后续访谈通过专家/组关系和父任务关联，但只追加新证据，不覆盖旧证据。
- 同一对象出现互相支持、反例、矛盾或明确否定时，建立独立证据集合并记录 `conflict_set`、`valid_from`、`valid_to` 和 `supersedes`；在人工审核前不得静默选择一方。
- 已批准版本的证据链保持不可变。后续证据只能形成候选变更或新版本，不能回写历史发布包。

#### 5.6.5 信息磨损硬门槛

- 可发布知识对象的原始证据回链率必须为 100%；任一无法定位原文的字段阻断发布。
- 原始 TXT 或受控政策来源的字节哈希、偏移、发言顺序/章节定位和时间戳（如有）不得因重新解析而改变；解析器升级只能生成新解析结果并保留旧结果。
- 任何摘要、推理、话术优化或人工改写都必须明确标记为派生内容，不得伪装成专家原话。
- 重复导入、跨次续访和冲突处理都必须保留审计记录，确保用户能区分“原始证据”“派生判断”和“审核决定”。

## 6. 系统架构与信息/数据流

### 6.1 已确认的职责边界

`Top 猎头访谈/讨论 → 独立平台：专家克隆知识更新、审核、版本管理与双 Prompt 编译 → 双 Prompt 发布包导出/人工交付 → 电话模型：执行专家克隆策略；下游评估平台：评价真实或测试电话与同版克隆基线的符合度`

- `ARC-001`【已确认】本产品拥有独立的平台边界、任务状态、知识存储、审核记录、版本管理和发布包管理，不依赖 Mentor 评估平台才能完成 MVP 闭环。
- `ARC-002`【已确认】MVP 通过发布包的人工复制、导出或文件交付向电话模型使用方和评价平台提供对应 Prompt；不建设与电话运行平台或 Mentor 评估平台的内嵌式集成。任何未来接口同步或自动发布需求都必须另立跨平台项目，不属于本产品当前路线。

### 6.2 专家学习循环

`当前专家知识基线与缺口 → 生成/维护访谈信息收集结构 → 开展访谈 → 导入 TXT → 提炼策略与话术 → 评估信息完整度 → 输出补访问题 → 下一次访谈或进入知识变更审核`

该循环允许一次访谈只补齐局部问题，不要求每次访谈都覆盖完整电话体系。

### 6.3 第一版可运行闭环（MVP v1）

经确认，当前优先目标是先跑通一条可观察、可回溯的最小链路，再用真实 case 迭代细化规则。第一版只要求：

`TXT 导入 → 原始快照/解析 → 目标专家确认 → LLM 辅助证据提炼 → LLM 辅助专家克隆结构提炼（候选 Graph/Fragment + 话术映射）→ 与基线 diff → G3 人工审核 → 新知识版本 → 基于同一已批准知识生成电话执行 Prompt + 策略评价 Prompt + 话术评价 Prompt → G5 发布确认 → 双 Prompt 发布包导出`

- 第一版允许使用简单字段、保守默认值和人工确认，不要求一次性实现复杂置信度校准、全量变更类型门槛、自动回归、复杂权限编排或动态 Overlay 引擎；最小角色/任务范围权限和敏感数据审计按 7.3 执行。
- 任何暂未实现的判断必须显式显示为“待确认/未实现”，不得静默推断或伪装成已批准知识。
- 实现必须遵循“PRD 决策 → PRD 获批基线 → 执行文档 → 分步实现 → 验证回写”的顺序；在 PRD 达到获批基线并生成执行文档前，不从本节直接派生代码或执行任务。
- 后续优化优先依据真实 case 暴露的问题回写 PRD，再升级 schema、审核规则和自动化能力。

### 6.4 下游平台观察（历史背景，非产品依赖）

2026-08-12 对 EVALLAB v0.6 进行了只读查看：

- 当前包含运行评估、文档测试集、评估报告、对话记录、模型配置、候选人 Agent、反应类型和评委 Agent 等模块。
- 支持模拟对话矩阵，也支持从飞书 Wiki/电子表格载入文档 case。
- 当前评委职责至少拆为业务效果、对话能力、策略命中检查和文档 case 判定四类 Prompt，使用变量槽位和结构化 JSON 输出。
- 上述实现仅用于帮助理解可能的下游使用环境，不构成本产品的集成协议、部署组成、Prompt 数量或字段契约；Mentor 已决定本产品单独建设。

## 7. 人工介入、复核与治理

### 7.1 条件确认点：目标专家识别

- 触发时机：交流记录完成结构解析和目标专家预识别后、候选策略证据抽取前。
- 自动放行：目标专家识别为高置信度，且不存在多个候选人或其他冲突。
- 人工触发：识别置信度低、存在多个合理候选人、元数据与正文冲突，或系统无法识别目标专家。
- 人工任务：从候选说话人中选择目标 Top 猎头，或手工补录。
- 提供的信息：候选标签、代表性原文、发言数量、时间戳范围、系统判断依据和置信度。
- 审计要求：保存系统初始判断、置信度、自动/人工放行方式、确认人和修改差异。

该确认点不要求人工逐一审核其他说话人的角色。

其他复杂确认点、风险处理、冲突裁决和置信度校准后置；MVP 最小人工确认点定义如下。

### 7.2 MVP 最小人工确认点与审批责任（OPEN-P0-04，已在本版本定义·MVP草案）

MVP 不要求人工逐句标注或逐一审核所有说话人，只在会改变知识归属、知识状态、风险边界或发布版本的节点介入。

| Gate | 触发条件 | 系统提供的复核包 | 最小责任角色 | 可选结果 |
|---|---|---|---|---|
| G1 目标专家确认 | 身份低置信度、多候选、元数据/正文冲突 | 候选说话人、代表性原文、时间戳、判断依据 | 产品/运营操作人 | 自动放行、选定、补录、仅存档 |
| G2 证据归类确认 | 证据类型、适用范围或目标对象无法可靠判断；存在冲突 | 原文 span、上下文引用、拟归类、冲突提示 | 知识审核人 | 接受、改类、请求补访、仅存档 |
| G3 知识变更审核 | 产生策略/节点/边/Fragment 连接/Overlay/策略 diff/话术 diff | 分层 diff、证据链、影响对象、版本关系 | 知识审核人 | 批准、驳回、请求补充/修改、仅存档 |
| G4 高风险政策确认 | 变更公司级 Guard、禁用规则、评分底线、敏感数据处理或强制动作 | 规则差异、风险说明、反例、适用范围 | 政策责任人 | 批准、驳回；无责任人则阻断 |
| G5 发布确认 | 新知识版本和发布包已生成 | manifest、版本、来源摘要、审核记录、回归状态 | 发布责任人 | 发布、阻断 |

#### 7.2.1 最小审批规则

- G1 只决定“哪些发言可作为目标专家证据”；高置信度且无冲突时可自动放行，不要求固定人工 Gate。
- G2 不要求人工重写原文。当前默认流程允许其作为 Graph 审核前后的后台工程：系统先做候选分类，Graph 详情呈现与结构/话术变化直接相关的证据，整图批准时逐项执行同一服务端校验并形成 G2 审计。目标归属不清、冲突、非法分类或证据不足时仍须显式退回人工复核/补访；隐藏逐条页面不等于自动放宽。原始 `utterance`、非法分类或目标专家资格未决的证据不得通过 G2。
- G3 覆盖所有会进入新知识版本的策略结构、话术结构、Fragment 连接和 Overlay 建立/修改。证据足够只代表可以生成提案，不代表可以发布。
- G4 只针对规范性或高风险变更；普通专家描述性知识不因进入某个专家组就自动触发 G4。
- G5 不能修改知识内容，只核对发布包引用的组版本、知识版本、Prompt/包哈希和审核记录是否一致；任何内容修改必须退回 G3。
- 同一人在 MVP 可以兼任操作人、知识审核人、政策责任人和发布责任人，但每个 Gate 必须留下独立的角色、决定、时间和理由记录；下游 Mentor/评价平台不承担本产品审批责任。
- 对象级 Gate 记录与任务级流程状态必须分开：界面同时显示“当前待处理 Gate”和“最近已完成 Gate”，且二者均由服务端同一状态机计算。批准单个节点/对象不得自动宣称整个任务已完成 G3；只有本次拟纳入新版本的对象集合全部完成所需审核、依赖关系完整且无阻断时，任务才可进入下一 Gate。

#### 7.2.2 审计最小字段

每次人工介入至少记录：`gate_id`、`task_id`、对象 ID/版本、审核角色、审核人、决定、决定时间、理由、证据引用、修改前后差异和后续状态。批准、驳回、仅存档和请求补充/修改均不可被静默覆盖。

### 7.3 MVP 最小权限与敏感数据治理（OPEN-P0-11，已在本版本定义·MVP草案）

MVP 采用“角色 + 任务范围 + 数据级别”的最小权限模型，默认拒绝未授权访问，不要求一次实现复杂 ABAC、跨组织租户或自动化 DLP。

#### 7.3.1 数据级别

| 数据级别 | 内容 | 默认处理 |
|---|---|---|
| `D1_delivery` | 已发布 Prompt、发布包 manifest、输入/输出契约、变更摘要、哈希和核验卡 | 可交付给下游评价使用方；不含原始访谈和候选人/JD 原文。 |
| `D2_knowledge` | 已批准/候选知识、策略结构、话术、差异、证据 span 和审核记录 | 仅授权的内部产品/运营、知识审核和政策责任角色按任务范围查看。 |
| `D3_sensitive_source` | 原始 TXT、实名说话人、候选人画像、JD/上下文原文、完整时间线和可导出的原始证据 | 默认最小化展示、界面脱敏；仅任务负责人/知识审核者，或经临时授权的政策责任人在必要任务范围内查看，原文导出需显式理由和审计。 |

发布包不得夹带 `D3_sensitive_source`；证据回链保留对象 ID、session/span 定位和受控引用。下游 Mentor/评价平台只接收 `D1_delivery`，不获得本平台原始资料访问权。

#### 7.3.2 MVP 角色权限

- **产品/运营操作人**：可创建任务、导入原始 TXT、查看自己负责任务的 `D2`，在 G1/G2 范围内处理确认；仅在任务必要时查看 `D3`。
- **知识审核人**：可查看所负责任务的 `D2` 与必要的 `D3`，审核证据和知识变更；不得把原始资料直接放入发布包。
- **政策责任人**：默认查看政策候选、差异、风险说明和必要证据；只有为判断敏感数据/高风险规则确有必要时，才临时查看相应 `D3`。
- **发布责任人**：可查看已批准版本、Prompt、manifest、回归状态和 `D1` 交付物；默认不开放原始 TXT、候选人/JD 原文。
- **下游评价使用方/Mentor**：只接收明确交付的 `D1` 发布包，不拥有本平台任务、证据或原文浏览权限。

MVP 可允许同一人兼任多个角色，但每次访问仍按实际角色记录；角色兼任不扩大任务范围，也不取消 G4/G5 的独立审计记录。

#### 7.3.3 查看、导出、保留与审计

- 原始 TXT 和 `D3` 内容在界面默认脱敏/按片段展示；需要显示实名或完整上下文时，操作者必须提供用途，系统记录授权角色、任务、对象、时间和理由。
- `D3` 原文下载/导出默认禁止；确有必要时由知识审核人或被授权的政策责任人发起一次性导出，记录导出文件哈希、范围、接收方、到期/删除时间（如适用）和审批理由。MVP 不提供批量无审计导出。
- 原始证据在仍被任务、已批准知识版本或发布包引用期间不得静默删除或覆盖。MVP 不自动清理；需要归档、脱敏或删除时，必须先记录影响并使无法回链的对象标记为不可发布/需重新取证，再执行带审计的人工操作。
- 所有查看敏感字段、下载/导出、脱敏、权限变更、交付和删除/归档事件写入不可变 `access_audit`，至少记录：操作者、角色、任务/对象 ID、数据级别、动作、时间、理由、结果、文件/Prompt 哈希和后续状态。
- 发现误授权、错误交付或哈希不匹配时，立即将对应访问/交付记录标记为异常，停止继续分发并重新走 G5/交付核验；MVP 不承担外部系统自动撤回。

#### 7.3.4 本地部署与凭据边界（v0.38 补充·硬约束）

- `api_key`、Token 等凭据不得写入代码仓库、项目 ZIP、演示数据库或可交付备份；仅保存在项目目录外的本机受控配置/环境变量或后续密钥服务中。失效凭据仍按 D3 处理，不因失效而允许传播。
- `127.0.0.1` 不是授权机制。只要接口可读取 D2/D3、修改 LLM 配置、触发模型调用或执行 Gate，就必须限制允许的前端 Origin，并采用最小会话/任务授权；不得用 `Access-Control-Allow-Origin: *` 向任意网页开放读写接口。
- 安全配置的普通读取只返回“是否已配置”和必要的非敏感参数，不返回可用于识别凭据的完整值；配置修改、连接测试和模型调用须记录操作者、任务/用途、结果和审计 ID。

## 8. 版本、差异与变更管理

以下版本治理规则已确认；具体差异展示、审批角色和回滚操作仍待细化：

- `VER-001`【已确认】已批准的知识基线版本、策略话术组版本和已发布双 Prompt 发布包版本均不可被原地改写。
- `VER-002`【已确认】新访谈产生的抽取结果先作为候选知识/变更提案保存；它可以被补充、驳回、仅存档或继续比较，但不会自动覆盖旧版本。
- `VER-003`【已确认】只有人工批准的变更提案才能生成新的知识基线或策略话术组版本；新版本必须保留其父版本、变更摘要、证据引用、审核记录和生成时间。
- `VER-004`【已确认】旧版本、被拒绝提案和仅存档证据都必须保留可查询关系，不得为了“清理”而破坏历史追溯链。
- `VER-005`【待讨论】版本回滚、并行生效、有效期和废弃后的评价任务处理方式待定义。

已确认：知识基线版本与双 Prompt 发布包版本分开管理。前者描述批准后的专家克隆知识状态，后者描述由特定知识基线和适用政策编译出的下游执行/评价交付物。

同一专家体系内部，策略结构变更与节点话术变更必须分层展示：

- 策略 diff：节点、边、触发条件、分支、线路、Guard、Graph/fragment 作用域。
- 话术 diff：节点绑定、段落功能顺序、句法结构、句式、用词与语感。
- 跨层影响：策略节点新增/拆分/合并/废弃时，列出受影响的话术与评价规则，但不得因此把两层合并为一个对象。

## 9. 产品运作与运行状态

### 9.1 当前产品人员使用顺序（已确认）

1. 在工作台导入新的飞书会议 TXT；若同一文件曾经跑过但需要从头学习，显式选择“新建干净重跑任务”，从 G0 开始，不沿用旧任务 Gate 和候选状态。
2. 在“任务与专家”确认本次目标专家，并明确选择不可变 Graph 基线。没有基线时按空基线学习；已有手搓或公共 Graph 时先导入为不可变参考基线，缺失证据、话术等字段允许为空。
3. 发起整份访谈增量学习。系统完整读取精确基线和新访谈，后台完成证据分类并输出相对该基线的候选节点、边、触发器和节点话术变化。
4. 在“Graph 审查”查看物化后的完整候选图，而不是只看增量对象：
   - 审核新增/修改/废弃结构及其目标专家证据；
   - 对节点选择一条或多条专家原话，必要时回听录屏后保存校准版本；
   - 对问题边直接校准一段路由条件，模糊但有意义的条件可以保留；
   - 可编辑继承自导入基线的节点和边，保存时形成候选 `modify`，不改原基线；
   - 电话流程阶段和左右区域只用于提升可读性，独立保存，不改变策略知识。
5. 只有目标专家归属、证据/基线引用、Graph 完整性和问题边条件均通过时，才可批准整张候选 Graph。多出口空条件继续阻断，系统不得代填未知业务语义。
6. 在“Prompt 与发布”从同一已批准 Graph 编译电话执行 Prompt、策略评价 Prompt、话术评价 Prompt及综合评价版本；核对共同 Graph/路由/话术选择身份、哈希和回归状态后走 G5。
7. 导出自描述发布包并人工交付。电话模型使用执行产物，评价 Agent 使用评价产物；两端必须记录同一发布包版本，不自动选择或融合专家。

### 9.2 运行状态表达

- 页面必须区分：业务任务状态、后台 LLM 运行状态、Gate 状态、布局分析状态和前后端连接状态。“后端已连接”只表示服务可访问，不表示提炼、审核或发布成功。
- 长时间 LLM 任务允许后台继续运行；客户端断开、刷新或页面切换不得被误报成模型失败。用户回到任务后应能看到最终候选或明确失败原因。
- LLM API 不可用时，已有 Graph 的浏览、人工编辑、Gate 校验、确定性物化、导出和非 LLM 编译能力不得被无关阻断；确实依赖 LLM 的动作须显示可恢复错误。
- 运行配置不得包含在项目 ZIP 或发布包中。API Key 仅保存在项目目录外的本机受控环境中，设置页和普通接口只显示是否已配置及脱敏状态。

## 10. 目标、北极星指标与评价体系

### 10.1 当前阶段目标

当前阶段的第一目标不是自动优化猎头策略，而是用尽可能少的人工通读成本，产出一套忠实、无损、可回听、可人工校准的单专家克隆 Graph，并从同一版本稳定生成执行/评价产物。先判断“是否像这位专家”，再在独立派生层讨论效果、合规或跨专家优化。

### 10.2 MVP 硬质量门槛

- 可发布策略、边条件和节点话术对其声明的原始证据回链率为 100%；人工校准文本必须同时保留不可变初始版和回听位置。
- 非目标说话人直接归因、跨任务/跨 Graph 引用、候选对象进入 approved-only Prompt、已批准基线被原地改写的容忍数均为 0。
- 同一输入身份重复物化、编译和导出须产生一致内容与哈希；布局调整不得改变 Graph、路由表或 Prompt 哈希。
- 完整访谈、基线结构、已选话术和规范路由条件不得被固定字符数或固定条数静默裁剪。因模型/总预算无法完整处理时必须显式失败或进入可审计分批流程。
- 多出口边完全缺少条件、同源同条件却指向不同目标、悬空端点或非法基线引用必须阻断批准/编译；非空但模糊的信息不得因字段不全被误判为否定或丢弃。
- 用户必须能在 Graph 主审核面完成结构定位、证据查看、原话选择/校准、边条件校准、继承基线编辑和发布前阻断理解，而不被迫逐条重听整场访谈。

### 10.3 观察指标与未定阈值

不能以“抽取出多少节点”或“是否形成完整树”作为单一成功指标。真实 case 迭代应同时观察：从导入到可审核 Graph/可发布包的耗时；人工采纳、修改、驳回比例；结构/话术证据可追溯率；关键未知项和补访问题是否减少；执行 Prompt 对专家路线和表达的忠实度；评价 Prompt 与人工判断的一致性；重复运行稳定性。除上述硬门槛外，样本集、量化阈值和专家相似度标尺仍归 `OPEN-P1-07/08`，不得凭当前单个 Looper case 虚构达标数值。

## 11. 非目标与明确不做事项

- `NOGO-001`【已确认】MVP 不承担真实 AI 猎头呼出电话的运行时质量评分。
- `NOGO-002`【已确认】本产品不接入 Mentor 的 EVALLAB，也不以任何下游评估平台 API、可用性或部署状态为上线前提。
- `NOGO-003`【已确认】MVP 不替代下游候选人 Agent、反应类型、模型运行和评估报告模块。
- `NOGO-004`【已确认】本产品不管理微信文字沟通、推荐后跟进、面试或 Offer 等非电话环节的策略及评价标准；这些内容无需在每个发布包的“不适用范围”中重复枚举。
- `NOGO-005`【已确认】MVP 不自动融合多个专家，也不把模型优化、公司 Guard 或产品人员推测改写成目标专家本人策略；任何组合或优化结果须成为独立派生版本。
- `NOGO-006`【已确认】MVP 不因信息模糊或字段缺失自动发明、补全或反转路由条件；完全未知的业务语义交由人工补充或补访。
- `NOGO-007`【已确认】电话流程阶段、左右反应区域、像素坐标和布局 LLM 结果只服务可视化，不进入运行 Prompt，也不作为策略知识或评价结论。
- `NOGO-008`【已确认】MVP 不声称仅凭访谈/模拟材料已经复现目标专家的真实通话轨迹、真实业务结果或完整隐性技能。

## 12. 开放问题

1. `MENTOR-Q-001`：信息完整度以体系闭环自洽、必采信息结构或两者共同判定？
2. `MENTOR-Q-002`：所有电话策略共同的最小必采信息结构是什么？哪些允许因专家风格而不适用？

## 12.3 MVP 集成验收发现（v0.37，执行回写）

本节不是放宽既有硬约束，而是将 G-01/G-02 实测暴露的实现细节归因回 P0，供后续真实 case 继续复核：

- **P0-03 / P0-13：证据引用规范化。** LLM 可能返回 `utterance_id` 而非证据层 `evidence_id`。新建知识对象必须在写入前将可解析的发言引用规范化为对应证据 ID；历史已批准对象不可原地修改，验收可暂时通过证据→发言的间接回链识别并计数。未知引用仍应阻断进入审核/发布。
- **P0-11：D3 默认接口行为。** 在 MVP 尚无身份认证上下文时，来源快照接口只返回来源元数据、`snapshot_available` 和脱敏标记；发言查询默认不返回正文。解析和 LLM 内部流程可读取本地不可变快照，但 UI/API 不得因“只读”而默认暴露 D3 原文。后续接入真实身份、任务范围和用途审计后，再设计受控的原文查看例外。
- **P0-07 / P0-08：阻断验收。** approved-only 编译、Prompt/manifest 哈希、发布包交付状态已通过现有演示任务连续性检查；超预算和真实 LLM 失败重试未在本轮触发，仍保留为下一轮安全回归用例。
- **P0-12 / P1-09：前端验收。** F-01 至 F-04 已完成 HTTP/DOM 契约检查；当前执行环境无可用浏览器实例，截图级视觉验收不记为已通过，不改变已确认的布局与信息密度方向。

## 12.4 转移基线复核与硬约束拉齐（v0.38，执行回写）

2026-08-25 对转移后的完整项目包完成代码、数据库、API 与真实浏览器复核。当时的结论是：项目文件可作为修复代码底座，但演示数据库、编译/发布产物和“expert-aware 已完成”记录不能直接视为获批业务基线。以下七项随后已在执行阶段 J 的服务端校验、隔离回归和页面状态中完成；本节保留为转移审计记录，不再代表当前实现仍未进入执行基线。

进入下一版执行基线前至少满足以下验收：

1. 使用伪造 LLM 输出把非目标说话人标为策略时，候选写入和 G3 均明确阻断；明确认可按 `SPK-010` 保留双重引用，不伪装为直接原话。
2. 修改目标专家、选定基线、有效采样参数、模型配置、提示词模板或输出 Schema 后，旧 `analysis_run` 不得复用；相同输入复用时界面明确展示原运行信息。
3. 原始 `utterance` 不能通过 G2；已批准证据的重新分类形成新候选/版本，不被 LLM 静默覆盖，也不会因“已批准”永久卡死在未分类状态。
4. 提炼、diff 与话术映射使用用户明确选定的同一基线；导入话术不修改 `immutable` 基线，内容哈希始终可复算一致。
5. 不存在/不匹配的任务或组无法取得其他任务的编译输入、编译产物、发布包和 Gate；切换任务后页面不保留上一任务选择。
6. 任务页、上下文栏和 Gate 详情对“当前待处理/最近已完成”的含义一致；批准一个对象不会让未完成对象集合越过 G3。
7. 正式转移包不携带 API Key；本地 API 不以通配 CORS 暴露证据正文、配置修改和 Gate 写操作。

当前包中已有的旧候选、重复/测试基线、无任务归属编译产物和不一致 Gate 记录须隔离、迁移或重建，不能通过修改展示状态包装为已验收数据。相关修复及验证事实见执行文档阶段 J。
