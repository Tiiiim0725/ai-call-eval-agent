## 0. 执行约束

1. 本文档只能作为候选方案和审议材料；未经主 PRD 回写和批准，不能作为执行文档的需求来源。
2. 延续主 PRD 已确认的边界：原始 TXT 不可变、基线不可原地改写、只选整套同一专家已批准策略话术组、候选和未批准对象不得进入 Prompt。
3. 所有“自动”都只是生成候选、对比或提示；不得跳过人工审核、变更版本化和发布门禁。

## 1. P0：执行基线

### OPEN-P0-02 最小知识 schema

### 1.1 实体和稳定 ID

| 实体 | ID 形式 | 最小必备字段 | 状态集 |
|---|---|---|---|
| 专家 `expert` | `exp_<slug>` | name, source_scope, created_at | active, archived |
| 策略话术组 `strategy_script_group` | `grp_<expert>_<slug>` | expert_id, purpose, current_version_id | draft, in_review, approved, retired |
| 策略 `strategy` | `str_<group>_<slug>` | group_id, applicability_scope, linkage_status | candidate, approved, superseded, archived |
| Graph / Fragment `graph` / `fragment` | `gph_...` / `frg_...` | group_id, nodes, edges, evidence_refs | candidate, approved, superseded, archived |
| Overlay `overlay` | `ovl_<group>_<base>_<slug>` | same-group `base_ref`, trigger, operation, evidence_refs | candidate, approved, rejected, archived |
| 节点 / 边 `node` / `edge` | `nod_...` / `edg_...` | parent_id, semantic_key, evidence_refs | candidate, approved, superseded |
| 触发 / 候选状态 `trigger` / `candidate_state` | `trg_...` / `cst_...` | condition, source_refs | candidate, approved |
| 话术 `script` | `spt_<node>_<slug>` | node_id, function, wording, evidence_refs | candidate, approved, superseded |
| Guard / 评价政策 `guard` / `policy` | `grd_...` / `pol_...` | scope, rule, severity, owner | candidate, approved, retired |
| 证据 `evidence` | `evd_<source>_<start>_<end>` | source_id, span, speaker, timestamp, kind | observed, contested, archived |
| 关联 `linkage` | `lnk_<from>_<to>_<kind>` | from_id, to_id, kind, evidence_refs | proposed, approved, rejected |

ID 一经创建永不重用；名称可改，ID 不改。所有可发布实体都必须带 `version_id` 、`parent_version_id` 和 `review_status`。

### 1.2 最小关系

`expert -> strategy_script_group -> strategy -> (graph|fragment|overlay) -> node -> (edge|trigger|candidate_state|script)`

`evidence -> evidence_refs` 可挂到任何候选或已批准对象；`policy/guard` 可挂到组或发布包。跨专家连接在 MVP 只能作为对比记录，不得直接写入组。

### OPEN-P0-03 证据与信息磨损

1. 导入时存档原始 TXT 快照：`source_id + sha256 + byte_length + captured_at`；原文只读，不允许在解析后覆盖。
2. 证据最小粒度为 `utterance` 和 `span`；每条证据必须保留 `source_id, utterance_id, start_char, end_char, text_hash, speaker_label, timestamp_start/end`。
3. 上下文窗口另存 `context_refs`，不把上下文文本拷贝成新证据；任何摘要都必须能反向原文。
4. 抽象对象只能通过 `evidence_refs` 派生；AI 归纳、推演和话术优化建议单独标记为 `derived` 或 `suggestion`，不能伪装成原始证据。
5. 跨次访谈采用追加而非覆盖；同一实体的矛盾通过 `conflict_set` 和 `valid_from/valid_to` 并存，由审核决定是否废弃旧版。

发布前硬门槛：所有可发布对象必须能回链至至少一条直接目标专家证据；无法回链的字段只能作为缺口或待确认项。

### OPEN-P0-04 人工确认点与责任

| Gate | 触发 | 系统输出 | 最小责任人 | 可选结果 |
|---|---|---|---|---|
| G1 目标专家 | 身份低置信度/冲突 | 候选人、原文、置信度 | 产品/运营审核人 | 选定、补录、仅存档 |
| G2 证据归类 | 目标专家已确认 | 证据类型、适用范围、冲突 | 知识审核人 | 接受、改类、待确认 |
| G3 变更审核 | 产生策略/话术/连接/Overlay diff | 分层 diff、证据列表、影响 | 知识审核人 | 批准、驳回、仅存档 |
| G4 高风险 Guard | 变更会改变禁止、评分底线或敏感数据处理 | 风险评估、反例、阻断原因 | 政策责任人（可与 G3 同人，但必须单独签名） | 批准、驳回 |
| G5 发布 | 新知识版本和 Prompt 编译成功 | manifest、回归、完整性检查 | 发布责任人 | 发布、阻断 |

人工审核必须记录身份、时间、结果、理由和差异。一人可兼任多个角色，但 G4 不能以默认勾选代替明示审批。

### OPEN-P0-05 变更提案与发布门槛

| 变更类型 | 候选最小证据 | 必须经过 | 可否直接发布 |
|---|---|---|---|
| `evidence_support` / `scope_change` | 1 条直接证据 + 适用范围 | G2, G3 | 否 |
| `add` / `modify` / `link` / `attach` | 1 条直接证据；连接类另需目标节点和边类型 | G2, G3 | 否 |
| `overlay` | 同一组已批准 `base_ref` + 触发条件 + 1 条直接证据 | G2, G3；如触及 Guard 加 G4 | 否 |
| `counter_evidence` / `contradiction` | 1 条直接证据；必须指向被影响对象 | G2, G3 | 否 |
| `replace` / `deprecate` / `override` / `reclassify` | 明示否定或者 2 条独立直接证据 + 影响范围 | G2, G3；高风险加 G4 | 否 |
| `split` / `merge` / `unlink` / `detach` | 被影响对象、连接理由、反例检查和回退方案 | G2, G3，必须回归 | 否 |

“证据足够”只允许生成候选提案，不等于可发布；所有发布必须同时通过 G3、G5 和对应回归门禁。

### OPEN-P0-07 Prompt 编译契约

- 编译输入只能是指定的一个已批准 `strategy_script_group` 版本、已批准政策与 Guard；候选、拒绝、待确认、仅存档对象一律排除。
- 编译产物必须包含 `source_versions` 、`policy_versions` 、`compiler_version` 、`prompt_sha256` 和生成时间。
- 优先级：禁止性 Guard > 评价政策 > 策略结构 > 话术文本 > 补充性建议；策略和话术在编译时分层渲染，不去重成一个无法追溯的大段。
- 超出长度不允许静默截断；只能分块、提示或阻断编译，Guard 与评分政策不得被省略。
- 编译后禁止直改 Prompt 文本；修改必须回到知识/政策源层重新编译，生成新版本和新 hash。

### OPEN-P0-08 发布包与人工交付

`manifest.json` 最小字段：`package_id, package_version, expert_id, group_id, group_version, knowledge_version, policy_versions, prompt_sha256, compiler_version, applicability_scope, included_object_ids, excluded_candidate_count, regression_run_id, created_at, approved_by, approved_at` 。

包内固定包含：`manifest.json` 、可复制 Prompt 、输入/输出契约、变更摘要、证据追溯清单、回归报告、交付检查表。交付时由接收人核对 package ID/version 和 prompt hash，回写 `delivery_receipt` 。

### OPEN-P0-09 描述性与规范性

- 默认专家范围：专家说过的做法、节点、话术、优先级和 case 细节，只对应一个 `group_id`，不自动升级为公司规则。
- 规范性范围：禁止操作、评分底线、敏感数据处理和发布必要条件。只能由明确政策所有者或专门审批升级，并标注 `scope=company` 与依据。
- 不同专家体系的相似表达不构成规范性政策；MVP 不进行自动交叉升级。

### OPEN-P0-10 证据型变更

`evidence_support` 提升支持强度；`counter_evidence` 降低适用范围或置信度；`contradiction` 建立冲突集并阻断发布；`explicit_rejection` 只生成废弃/替换候选；`scope_change` 只改变作用范围。这些变更不覆盖旧证据，必须记录 `supersedes` 、`effective_at` 和审核结果。

### OPEN-P0-11 最小权限与敏感数据

| 数据类 | 默认可见角色 | 导出默认处理 |
|---|---|---|
| 原始访谈/TXT | 任务创建者、知识审核人 | 禁止公开导出，必须脱敏并留审计 |
| 证据和候选知识 | 任务成员、审核人 | 仅导出与发布包关联的最小片段 |
| 已批准知识、Prompt | 产品/运营、审核人 | 可导出，必须携带版本与 hash |
| 交付包和回归报告 | 发布责任人、接收人 | 导出留 delivery_receipt 与审计记录 |

## 2. P1：MVP 设计与验证

### OPEN-P1-01 访谈提纲与补访循环

`information_schema` 由产品责任人版本化维护；系统按已批准基线、未决变更和缺口生成提纲候选，访谈者可编辑后才使用。每次访谈都新建 `session_id`，按 `expert_id + group_id` 追加到同一专家时间线，不覆盖旧记录。

补访停止条件：必采信息结构已覆盖，或剩余缺口不再阻断当前变更/发布，或连续两次补访没有新证据。报告分开展示结构覆盖、策略闭环、话术覆盖与待回收缺口。

### OPEN-P1-02 证据语境与假设回应

| 类型 | 可进入的层级 | 发布前要求 |
|---|---|---|
| 专家主动陈述/明示否定 | 可进入可复用规则或变更候选 | 直接证据 + 审核 |
| 回答访谈者假设 | 只进入候选，带 `case_scope` | 需要明示泛化或另外直接证据 |
| 具体 case 复盘 | 可进入单 case 候选或 Overlay | 必须绑定 case 和 base_ref |
| 转述他人 | 仅作为上下文 | 不得单独形成规则 |
| AI 归纳/推演 | 只作建议或待确认 | 不得作为证据发布 |

### OPEN-P1-03 置信度体系

将置信度拆为独立维度：`identity, parse, evidence_kind, structure, applicability, script, compatibility`，每维保留分数、依据、模型版本和校准状态；不压成一个“总分”。

候选阈值（首版待用样本校准）：`>=0.90` 仅允许身份识别自动放行；`0.75–0.89` 可继续生成候选但必须人工确认；`<0.75` 或任一关键维度冲突时阻断变更。阈值不得替代证据门槛，首版上线前须用黄金 case 校准。

### OPEN-P1-04 经验型多动作表达

每个候选用结构化 `action_set[]`：`action, priority, trigger, expected_state, alternatives[], unknowns[], stop_condition, evidence_refs`。展示时保留多条可行线索、优先级和未知选择因子；不把模型推演压成唯一路径。不完整的 action_set 只能存档或请求补访。

### OPEN-P1-05 任务生命周期与多次访谈

`created -> imported -> parsed -> extracted -> diffed -> review_pending -> approved -> compiled -> regression_pending -> released`

任一状态失败进入 `failed` 并保留原因；重试必须带相同 `task_id + source_sha256 + parser_version`并保持幂等，不重复生成版本。同一专家续访通过 `parent_task_id` 和 `session_id` 关联；重复导入只挂新证据，不覆盖旧任务。

### OPEN-P1-06 冲突与版本漂移

同一专家跨次访谈的矛盾采用附加证据 + 有效期并存；新证据不静默替换旧规则。只有明示否定、审核通过且新版本记录 `supersedes` 时，才能将旧对象标记为 `superseded` 或 `retired`；已交付的包不回写，新任务必须明示采用哪个版本。

### OPEN-P1-07 回归集与验收

建立版本化 `golden_case_set`，至少包含：正常首次触达、正常二次触达、不适用范围、证据冲突、说话人歧义、敏感 Guard、Prompt 超长和无证据话术。每次发布前对比旧版与新版：关键 Guard 不得退化，可发布对象必须 100% 可追溯，无法解释的新失败必须阻断发布。回归可以由本平台执行或人工/外部执行后上传，但必须记录执行环境、包版本、结果和操作人。

### OPEN-P1-08 北极星与产品验收

MVP 先采用“硬门槛 + 趋势指标”：

- 硬门槛：发布包 manifest 完整率 100%；可发布对象证据可追溯率 100%；高风险 Guard 回归无退化；冲突未解决时不得发布。
- 趋势指标：单任务从导入到发布的耗时、人工采纳/驳回率、关键未知项减少、续访后新证据增量、回归失败率。首轮只记录基线，不用单一分数判断专家好坏。
- 验收终点：使用一批脱敏的真实 TXT 和黄金 case 完成一次“导入→审核→发布→交付”演练，审核人能在交付后重新校验包 ID/version/hash。
